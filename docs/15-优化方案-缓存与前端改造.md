> 状态：**方案待评审，本轮只实现了标注为「已做」的部分**。
> 目标是减少数据库往返、降低首屏等待，并让清流前端在低配服务器上更稳。

## 二、后端还能优化的地方（按收益排序）

### 2.1 高收益：默认模型解析（已部分实现）

**问题**：前端调 `/v1/chat/completions` 不带 model 时，后端每次都要走
`resolveInboundModel` → `GetDefaultRouteModel` → 读链配置 + 读定价 + 查 Key。

**现状**：已有 `identityCache`，但**默认模型结果没有缓存**。

**建议**：给「链首位 → 默认模型」加 30 秒 TTL 缓存，键为 `chainCode`。

```go
// 伪代码
type resolveCache struct {
    mu    sync.RWMutex
    items map[string]cachedModel // key: chainCode
}
func (a *Application) GetDefaultRouteModel(ctx, chainCode) (...) {
    if hit, ok := a.resolveCache.get(chainCode); ok { return hit, nil }
    // ...原逻辑...
    a.resolveCache.set(chainCode, result, 30*time.Second)
}
```

调价/改链时可主动失效（`PutRouteChain` 成功后清空该 chain 的缓存）。

### 2.2 高收益：定价行按链预加载

**问题**：`routeChain()` 对每个候选逐条 `findActiveChainPricing`，6 条链 × 最多 10 个候选 = 最多 60 次查询。

**建议**：一次 `WHERE provider_id IN (...) AND model_code IN (...) AND task_type IN (...)` 批量取，再在内存里匹配。
预计把「AI 能力页首次加载」的查询数从 ~70 降到 ~8。

### 2.3 中收益：权限码解析缓存

**问题**：每个请求都过 `rbac.LoadPermissions`，对同一用户重复计算权限集合。

**建议**：以 `userId + roleVersion` 为键缓存 60 秒；角色变更时 bump `roleVersion` 使其失效。

### 2.4 中收益：`/api/me` 聚合缓存

清流每次刷新页面都会调 `/api/me`，内部可能触发工作台请求（租户名）。
**建议**：租户名已缓存；余额单独走 `/billing/balance` 并在前端做 30 秒节流，不放进 `/api/me`。

### 2.5 低收益但简单：静态资源与 ETag

Nginx 已对 `dist/assets/*` 加哈希缓存。建议给 `/api/clients` 列表加 `ETag`（基于 `max(created)+count`），命中的话返回 304，省掉一次 JSON 序列化。

## 三、清流前端改造方案（结构性）

### 3.1 当前问题

1. **首屏串行请求**：`/api/me` → 然后才渲染，卡片内容再各自请求，出现「先骨架后跳动」。
2. **轮询过密**：任务卡每 2.5 秒轮询，多任务时 N 个请求并发。
3. **状态分散**：客户、任务、文档各自 `useState`，跨页返回会重新拉取。
4. **移动端**：侧栏 + 表格在窄屏下挤压。

### 3.2 改造方案

#### 方案 A：请求合并（推荐先做）

把「首屏要用的数据」合并成一个接口：

```
GET /api/bootstrap?cid=xxx
→ { user, clients, jobs, documents, csrf }
```

一次往返换五个请求，首屏时间预计减半。

#### 方案 B：轮询单点化

把所有任务的轮询合并成一个 `GET /api/jobs?status=queued,running`，
由前端一个定时器统一刷新，替代每个任务卡各自的定时器。

#### 方案 C：乐观 UI

上传后立刻在前端插入一条 `queued` 任务卡，再等服务端确认，
避免「点了上传后界面没反应」。

#### 方案 D：分包加载

当前单包 302 KB。把「案例详情」「报告」「管理」拆成路由级 chunk，
首屏只加载登录/列表，预计首屏 JS 降到 ~120 KB。

#### 方案 E：移动端

- 断点 `≤768px`：侧栏改为抽屉
- 表格改为卡片列表（客户列表、任务列表已接近卡片式，改动成本低）

### 3.3 建议实施顺序

1. **方案 B（轮询合并）**——最容易，直接减少服务器压力
2. **方案 A（bootstrap 接口）**——收益最大
3. **方案 C（乐观 UI）**——体验提升明显
4. **方案 D（分包）**
5. **方案 E（移动端）**

## 四、风险与注意

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 缓存一致性 | 链/定价改了但缓存还在 | 写操作主动失效 + TTL 兜底（≤60s） |
| 首屏接口变大 | bootstrap 可能超过 100 KB | 限制 clients 只返回前 20 条，其余分页 |
| 轮询合并漏更新 | 单个任务失败未被感知 | 合并接口返回所有非终态任务，终态由页面刷新兜底 |
| 前端分包改动面大 | 路由与懒加载要一起改 | 先做方案 B/A，分包单独一轮 |

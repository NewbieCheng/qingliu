# 清流 V2 计划：解析优先级、积分计费、登录验证码与批量排队

> 状态：**已确认，按建议方案实施中**（2026-11-09）。
> 上一版计划见 `docs/计划-账号互通与PDF解析修复.md`（已实施并上线）。
>
> **进度会随每次改动更新到第 7 节。**

---

## 目标（Goal）

让清流成为一套「解析不白花钱、钱花在刀刃上、用户看得见进度」的流水审核工具：

1. **隔离**：团队登录看到的是团队资料，个人登录看到的是个人资料，两者**绝不共享**；默认团队「今天不加班」承接既有管理员账号。
2. **不浪费**：有文字层的 PDF 绝不调模型；只有本地兜底也失败时才提示用户花钱走视觉识别。
3. **不白扣**：解析成功才扣积分，失败自动不扣；同一文件不重复计费。
4. **看得见**：排队位置、当前阶段、百分比、用了哪条解析路径，全程可见。
5. **守得住**：登录必须过验证码，**直接复用工作台登录页的验证码交互**（点击式弹窗），不另造一套。
6. **扛得住**：2C/1G 服务器上，多用户批量上传不会打爆内存，排队有序。

验收口径：一个没积分的用户上传 PDF 会被立刻拦下并说清原因；一个有积分的用户上传扫描件，能一路看到「本地 OCR 失败 → 建议视觉识别 → 确认后按页扣费 → 识别完成」全过程。

## 0. 先说结论：你提的三件事，代码里是什么状态

我逐个查了代码，先把事实摆出来，再给方案。

### 0.1 PDF 解析优先级 —— 你说的「有字就取字，没字才调视觉模型」

**现在的实际行为**（`server/parser.go`）：

```go
// parser.go:90
func parseFile(ctx, b, name, source string, ocr bool, ...)
// parser.go:256
if ocr && (source == "credit_report" || source == "other") {
    tesseract ...   // 只有用户手动勾了 ocr，且只对征信/其他类型
}
```

问题有三层：

| 问题 | 现状 | 你的期望 |
| --- | --- | --- |
| 默认走哪条路 | 用 `pdftotext -bbox-layout` 提取文字层，**这一步是对的** | 一致 |
| 文字层为空时 | **不会自动降级**。只有用户勾了 ocr 才试，且只对征信/其他来源 | 应自动降级到视觉模型 |
| 视觉模型 | 用的是本机 `tesseract`，不是工作台的 `page-ocr` 模型链 | 应该是「本地没字才调模型」 |

所以你要的优先级链，现在是断的。正确链路应该是：

```
pdftotext 有字（≥阈值） → 直接用文字（0 积分成本，最快）
        ↓ 无字/字太少
   本机 tesseract（免费，兜底一层）
        ↓ 仍失败或质量差
   工作台 page-ocr 视觉模型（扣积分，最慢最贵）→ 仅在用户授权时自动使用
```

### 0.2 积分计费 —— 关键缺口

**现在的实际行为**：

- AI 分析（`statement_review`）：走了 `ExecuteChatBilled`，**工作台网关内部会扣积分**。这部分是通的。
- **本地解析（pdftotext / tesseract）：完全不扣积分**。这是你说的「就算用本地部署的东西解析也一样要扣」，目前没做。
- 前端没有「余额不足，无法解析」的前置拦截，要等任务失败才发现。

结论：需要新增**「解析服务」计价项**，本地解析也扣积分，并在提交时前置校验余额。

### 0.3 登录验证码 —— 你看到的现象是真的

**根因**：工作台 `POST /api/v1/auth/login`（网页端密码登录）**强制**校验验证码：

```go
// internal/auth/handler.go:339
// Password login must pass human captcha...
if strings.TrimSpace(request.Password) != "" && request.Code == "" && !h.skipCaptchaVerification {
    if request.CaptchaID == "" || request.CaptchaCode == "" { return ErrCaptchaRequired }
    if !h.captcha.Verify(...) { return ErrCaptchaInvalid }
}
```

但清流的登录走的是**服务端登录** `POST /api/v1/service/auth/login`，这个入口**刻意没有验证码**（注释写着「调用方已在自己的界面里认证了人类」）。

那个假设不成立——清流的登录页是**直接面向用户的**，所以实际上等于把工作台的验证码保护绕过去了。

所以：
- 清流登录页没有验证码：**是设计缺口，不是 bug**
- 注册页有验证码：已经有了（`RegisterForm` 里 `captcha_id`/`captcha_code` 是通）
- 需要补的是**登录**也要验证码

### 0.4 团队登录的资料隔离 —— 你说得对，这里没做

现在清流的数据模型 `ql_customers` 只有 `owner_user_id`，**没有租户/团队维度**。团队登录后看到的仍然是个人账号自己的资料。

要做到「团队和个人资料不共享」，需要给清流加**工作空间（workspace）维度**。这是一个数据模型变更，工作量最大。

## 1. 你的需求清单（我整理后的完整版）

### 1.1 解析优先级（P0）

1. PDF 有文字层 → 直接提取，不调模型，**默认路径**
2. 文字层为空 → 自动降级到本机 tesseract
3. tesseract 也失败 → 提示用户可选择「用视觉模型重试」（因为要扣积分，必须用户知情）
4. 用户上传时可直接选「优先视觉模型」，但界面上要明确标注「更慢、消耗积分更多」

### 1.2 积分计费（P0，核心）

1. **本地解析也要扣积分**，作为独立计价项进入定价体系
2. 提交解析前**前置校验余额**，不足直接拒绝并给出明确提示
3. 余额不足时，上传按钮置灰 + 提示「积分不足，请联系管理员充值」
4. 定价可配置：每份文档多少积分，按页数阶梯可选

### 1.3 登录验证码（P1）

1. 清流登录页增加图形验证码，与工作台完全一致
2. 团队登录同样要求验证码
3. 验证码错误可刷新重试，不清空已填账号密码

### 1.4 团队资料隔离（P1）

1. 引入工作空间维度：`ql_customers` 增加 `workspace_id`
2. 团队登录 = 进入团队工作空间，看到团队资料
3. 个人登录 = 进入个人工作空间，两者严格隔离
4. 团队成员可被邀请进入同一工作空间（复用工作台租户成员关系）

### 1.5 批量排队与并发（P1）

1. 支持一次上传多个 PDF
2. 队列化：先入队，后台串行/有限并发处理
3. 并发上限按服务器能力定（当前 2C/1G，建议 1~2 个解析任务并发）
4. 多用户同时上传：先到先得，同一个用户的多份文件之间也排队

### 1.6 用户体验（P1）

1. 每个任务显示：排队位置、预计等待、当前阶段、百分比
2. 批量上传显示总体进度（如 3/10 完成）
3. 解析失败给出可操作建议，不是一句「解析失败」

### 1.7 历史清理（P2）

1. 删除无用的旧备份
2. 删除无用的旧迁移

## 3. 实施方案

### 阶段 A：解析优先级链（不含计费）

**目标**：有字取字，没字降级，只有兜底才花钱。

```
1. pdftotext 提取全页文字
2. 判断有效字数（去掉空白/页码后的字符数）
   - 每页平均 ≥ 30 字 → 判定「有文字层」，直接用
   - 否则标记 needs_ocr
3. needs_ocr 时：
   a. 本机 tesseract 逐页识别（免费）
   b. 若仍 < 阈值 → 标记 needs_vision
4. needs_vision 时：
   - 默认不自动调模型，返回「建议使用视觉识别」状态
   - 用户点击确认后才调 page-ocr 链（扣积分）
```

**改动文件**：
- `server/parser.go`：提取与降级逻辑
- `server/worker.go`：新增 `needs_ocr` / `needs_vision` 阶段
- `server/store.go`：任务增加 `method` 字段记录用了哪条路
- 前端 `TaskList.jsx`：显示「文字提取 / 本地 OCR / 视觉识别」

### 阶段 B：积分计费（核心）

**新增计价项**「文档解析」：

| 计费点 | 计价方式 | 建议默认值 |
| --- | --- | --- |
| 文字层提取 | 按份 | 1 积分 |
| 本机 OCR | 按页 | 0.5 积分/页 |
| 视觉识别 | 按页 | 按模型实际 token 计费（走网关） |

**关键设计决策（需你确认）**：

- 方案一（推荐）：**成功后扣费**。任务成功才扣，失败不扣。简单、用户不会有「白扣钱」的感觉。
- 方案二：预占 + 结算。提交时预占，成功按实结算，失败释放。更精确但复杂。

我建议**先做方案一**，因为当前服务器规模不需要预占的复杂度。

**实现**：
- 工作台新增 `POST /api/v1/service/billing/charge`（服务到服务，幂等）
- 清流解析成功后调用，`batch_trace_id = "qingliu-parse-" + jobID`
- 提交前调 `GET /api/v1/account/balance` 校验余额

### 阶段 C：登录验证码（复用工作台交互）

**原则：不另造一套验证码 UI。** 工作台的 `CaptchaVerifyDialog` 是点击式验证码弹窗
（`click_largest` / `click_smallest` / `click_sequence` 等），清流直接复用同一交互模式与同一后端。

**改动**：
1. 工作台 `internal/auth/handler.go`：`serviceLoginRequest` 增加 `captcha_id`/`captcha_code` 并**强制校验**（已完成）
2. 清流 `server/workbench.go`：`login()` 透传验证码（已完成）
3. 清流 `server/main.go`：`/api/auth/captcha` 归一化为 `{captcha_id, type, svg, prompt, icon_target, sequence}`（已完成）
4. 前端 `CaptchaField.jsx`：按工作台同款交互实现（SVG 渲染 + 点击选点 + 刷新）
5. 登录页与注册页共用同一组件

**已完成 / 待补充**：
- [x] 工作台服务端强制校验
- [x] 清流透传验证码字段
- [x] 验证码接口字段归一化
- [ ] 前端点击式验证码交互（当前是字符输入，需升级为与工作台一致的点击式）
- [ ] 注册页发码前也走同一验证码

### 阶段 D：团队资料隔离（P0，最高优先级）

**为什么必须做**：现在 `ql_customers` 只有 `owner_user_id`。团队登录后看到的
仍是个人账号自己的资料 —— 甲乙两家公司的客户流水、征信报告会互相可见。
对一家做金融流水的产品，这是**合规级缺陷**，不是体验问题。

**核心语义（按你的确认修订）**：

个人登录**不是「没有团队」**，而是**他自己就是一个独立的团队**。所以隔离是三层：

| 谁 | tenant_id | 能看到 |
| --- | --- | --- |
| 公司团队账号 | > 0（如「今天不加班」=1） | 整个团队的资料，团队内成员共享 |
| 个人账号 | 0（个人空间） | **只有自己创建的**资料 |
| 管理员 | 同所属空间 | 同样受限，**不再跨团队全见** |

关键修正：原设计里「管理员无条件放行」和「个人用户只看 owner」是两套逻辑，
必然分叉出「列表看不到、输 ID 能打开」的越权。现在收敛成一个函数
`scopeWhere(user, alias)`，**授权判定 `allowed()` 与列表查询共用它**。

**默认团队归属**：生产环境已存在 `t_tenant.tenant_id=1 / tenant_name='今天不加班'`。

1. 既有清流账号（admin/sales/reviewer，都是这家公司的运营）由迁移归入 tenant 1
2. 新注册的个人账号 `tenant_id=0`，进自己的个人空间，与团队彻底隔离
3. 工作台上没有租户的管理员首次登录清流时，自动落 tenant 1（`defaultTeamTenantID`）

**数据模型**（复用工作台租户，不另建 workspace 表）：

```sql
ALTER TABLE ql_users
  ADD COLUMN tenant_id BIGINT UNSIGNED NOT NULL DEFAULT 0,   -- 0=个人，>0=公司
  ADD COLUMN tenant_role VARCHAR(16) NOT NULL DEFAULT '',
  ADD KEY idx_users_tenant (tenant_id);

ALTER TABLE ql_customers
  ADD COLUMN workspace_tenant_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
  ADD COLUMN owner_user_id CHAR(32) NOT NULL DEFAULT '',      -- 审计 + 个人空间判定
  ADD KEY idx_customers_tenant (workspace_tenant_id);
```

迁移 `server/migrations/003-tenant-isolation.sql` 幂等，含回填与孤儿数据处理。

**验收标准**：
- 团队账号 A 登录，看不到团队 B 的任何客户
- 个人账号登录，看不到自己所属团队的客户
- `admin` 登录看到「今天不加班」团队的客户
- 用别人的客户 ID 直接请求，返回 404（不是 403，避免泄漏存在性）

### 阶段 E：批量排队与并发

- 单批最多 20 个文件，单文件 20MB，单批 100MB
- 队列：`ql_jobs` 已有，增加 `priority` 与 `queued_at`
- 并发：worker 从 1 个提升到可配置（默认 2）
- 显示排队位置：`SELECT COUNT(*) FROM ql_jobs WHERE status='queued' AND seq < ?`

### 阶段 F：历史清理

- 备份保留策略：只留最近 5 份
- 迁移文件：保留全部（迁移是历史记录，删了会导致已有环境无法追溯）——**这条我建议不改，需你确认**

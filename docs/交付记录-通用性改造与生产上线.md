## 一、这次真正解决的核心问题：通用性

用户的原话是：

> "我要求修复的是后面的通用性……不是这个东西修复之后，其他的别人上传一个另一个东西过来，它又不支持了……代码写死只是兜底，快速匹配模式……匹配不到就要 AI 兜底。"

之前的做法是**给具体格式打补丁**（微信怎么解析、支付宝怎么解析、招行怎么解析）——换个银行就又不支持了。这次改成**分层架构**：

```
规则快路径（毫秒级，零成本）
   ↓ 可用率 ≥ 80%
   ✅ 直接出结果
   ↓ 可用率 < 80% 或 0 行
AI 兜底（不思考模式，秒级，按量计费）
   ↓
统一结果契约（同一套质检、同一套导诊、同一套入库）
```

### 三条改动（这才是通用性）

| # | 位置 | 旧逻辑 | 新逻辑 |
| --- | --- | --- | --- |
| 1 | `structure_rescue.go` `shouldTryStructureRescueAfterOCR` | `if len(Rows) > 0 { return false }` —— **只要抽出一行，AI 永远不介入** | `needsAIRescue()`：零行 **或** 可用率 < 80% 就放行 |
| 2 | `ai_analysis.go` `tryEnhanceScanWithWorkbenchOCR` | `if len(Rows) > 0 { return }` | 同一判断函数，两处闸口统一 |
| 3 | `structure_rescue.go` `structureRescueInput` | 只读 `ocr_text`/`extract_text`，CSV/XLSX 永远为空 → 兜底等于不存在 | 为空时回退到**已解析行的 `raw` 原文** |

### 配套的容错化（让 AI 的输出真能被用上）

| 位置 | 旧 | 新 |
| --- | --- | --- |
| `ocrDateTimeRE` | `^(\d{4}-\d{2}-\d{2})\s+(\d{2}:\d{2}:\d{2})\s+` 强制横线+时分秒 | 横线或紧凑日期、时分秒可省略 |
| `parseOCRTranscript` | 直接解析，AI 输出 Markdown 表格就崩 | 先 `tidyTranscript()` 去竖线/分隔行，再解析 |
| `applyStructureRescueResult` | 无条件覆盖 | **AI 结果更差时保留原结果**（安全阀） |

## 三、具体格式的解析修复（快路径优化）

这些不是通用性，是让常见格式别去消耗 AI：

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| mx 19 页流水 675 行全 invalid | 单列金额是**负数**，代码见到负数直接判失败 | 负号即流出；正数即流入；零金额中性 |
| 微信/支付宝 CSV 全 invalid | 只有「交易时间」列（带时分秒），被映射到 `time` 而非 `date` | `date` 为空时从 `time` 取日期段 |
| 微信/支付宝金额列认不出 | 列名是 `金额(元)`，别名是 `金额` | 别名支持「别名 + 括号单位」前缀匹配 |
| 支付宝「不计收支」行被判失败 | `收/支/其他` 不在方向别名里，零金额又被判死 | 补别名；零金额 + 明确中性 → 合法中性行 |

**mx 结果：invalid 从 675/675（100%）降到 19/675（2.8%）。**

## 四、参数归一（清流不再写死任何模型参数）

新增 `server/wb_limits.go`：

```go
// 清流不声明"要多少 token"，只说"给我解析结果"
"max_output_tokens": wbMaxOutputTokens(ctx, userID)  // 后端定价表说了算
"reasoning": {"effort": wbReasoningEffort(ctx, userID)}  // 后端说了算，映射由后端做
```

优先级：环境变量（应急）→ 后端 `/v1/models` → 官方兜底 393216。
**代码里不再出现任何模型相关魔法数字。**

## 五、后端改造（不加班）

### 5.1 Responses 嵌套 reasoning（关键 bug 修复）

```go
// 旧：扁平字段，DeepSeek 的 Responses 规范不认 → 上游默认开思考 → 正文被截断
ReasoningEffort *string `json:"reasoning_effort,omitempty"`

// 新：嵌套结构
Reasoning *responsesReasoning `json:"reasoning,omitempty"`  // {"effort":"none"}
```

### 5.2 不做全局 off→none（尊重每模型兼容差异）

用户明确指出：`none` 只是 DeepSeek 的写法，其他模型可能用 `off`、`null` 或不支持。

所以映射**按模型配置驱动**，数据源是定价表的 `thinking_level_map_json`：

| 厂商 | 映射 | 含义 |
| --- | --- | --- |
| DeepSeek | `{"off":"none"}` | off → 转发 none |
| Claude | `{"off":null}` | off → 不写该字段 |
| 部分模型 | 未配置 | 原样转发 |

新增 `MapReasoningEffort(effort, levelMap)`，**不写任何厂商专有分支**。

### 5.3 上限放开

| 参数 | 旧 | 新 |
| --- | --- | --- |
| `max_tokens_cap` | 32768 | **393216**（官方上限，语义降级为"保险丝"） |
| `auto.max_output_tokens` | 30000 | **393216** |

迁移脚本：`migrations/000099_llm_gateway_max_tokens_cap_384k.{up,down}.sql`

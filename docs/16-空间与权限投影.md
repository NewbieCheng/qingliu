# 16 · 空间与权限投影

> 2026-11 起，清流的「团队」不再由清流自己定义，而是**工作台身份的投影**。
> 本文是这一层的现状与不变量；改动前先读 [03-数据模型](03-数据模型.md) 与 [11-工作台后台](11-工作台后台.md)。

## 1. 要解决的两个问题

改造前有两个「团队」同时在跑，且都不完整：

| 问题 | 表现 |
| --- | --- |
| **空间切不了** | `ql_users.tenant_id` 在**登录时**就定死为工作台返回的那一个。一个人在工作台同时属于「企业」和「自己的个人账号」时，清流只能二选一，切过去就回不来。 |
| **权限会降级** | `ql_users.role` 是清流自己的三档（admin/sales/reviewer），而工作台是 RBAC 权限码。`wbUpsertLocalUser` 把不认识的 `service_role` 一律写成 `sales` —— 于是工作台的 `enterprise_member_readonly`（只读成员）在清流里能上传、能核对、能签发。 |

两条都被「让工作台当唯一真相」修掉了。

## 2. 空间（Space）

### 2.1 真相在会话上

```text
ql_sessions.tenant_id  →  这个会话当前在哪个空间（0 = 个人空间）
ql_users.tenant_id     →  账号的**默认**空间（登录时落这里）
ql_customers.workspace_tenant_id / owner_user_id  →  资料归属（未变）
```

`scopeWhere(user, alias)` 读的是**会话**，不是用户列：

```go
// 团队空间：只看本企业资料
alias + ".workspace_tenant_id = ?"                  // = session.tenant_id
// 个人空间：只看自己创建的资料
"(" + alias + ".workspace_tenant_id = 0 AND " + alias + ".owner_user_id = ?)"
```

> 老会话没有 `ql_sessions.tenant_id` 时用 `COALESCE(NULLIF(s.tenant_id,0), u.tenant_id)` 兜底，行为与迁移前一致。

### 2.2 谁能进哪个空间

**清流不自己判断**。切换之前先问工作台 `GET /api/v1/me/spaces`，由工作台按主身份 + `t_tenant_membership` 算出列表；清流只做展示与保存选择。

工作台侧的两个接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/me/spaces` | 返回个人空间 + 全部有效企业成员关系，`current` 标记当前 |
| POST | `/api/v1/me/switch-space` | body `{tenant_id}`，先校验成员资格，再换发带空间声明的 access token |

工作台的**空间声明落在 `t_refresh_token.space_tenant_id / space_account_type / space_role`**，`VerifyAccessToken` 回库读它而不是信 JWT —— 被移出企业后旧 token 立刻失效，不需要等过期。

### 2.3 切换的语义

- 只改**本会话**一行，不影响同一个人在其他设备上的登录。
- 切换后工作台可能同时换发新的 access token（空间变了令牌也要变），清流把它加密写回 `ql_workbench_accounts`，否则后续计费仍按旧空间扣。
- 前端切换成功后**清空全部查询缓存并整页重载**：空间一换，客户列表、余额、操作记录全换视角；只刷新当前页会让首页继续显示上一个空间的客户，那是比报错更糟的越权感。
- 工作台在响应里给出空间信息；清流拿不到企业名时显示「企业 #id」，**不要**用 `/api/v1/tenant/info` 猜 —— 那个接口按当前令牌返回名字，用它命名另一个空间会显示成错误的公司。

## 3. 权限投影

### 3.1 判定入口只有一个

```go
q.can(code)        // server/permissions.go
q.isAdmin()        // = q.can(permAdmin)
q.canWriteCase()   // = q.can(permCaseWrite)
q.canSignReport()  // = q.can(permReportSign)
```

handler **不要**再写 `role == "admin"`。新增权限：先加常量 → 映射进 `rolePermissions` → 在 handler 用 `q.can(...)`。

### 3.2 快照优先，role 只做兜底

登录时 `wbSaveLogin` 把权限码快照存进 `ql_workbench_accounts.permissions`（JSON 数组）：

```go
codes := loginPermissions(serviceRole, strList(user["permissions"]))
// 1) 工作台真返回了 permissions → 直接用
// 2) 没有 → 按 service_role 查 rolePermissions
// 3) 都没有 → nil（退回 legacyAllowed 的三档判定）
```

判定规则：

- **有快照时只看快照**，不再叠加 `ql_users.role` —— 否则降级会被 role 里残留的旧值抵消。
- **没有快照时**（本地过渡账号、迁移前登录的老会话）走 `legacyAllowed`，语义与改造前逐字一致。
- 快照解析失败（形状不对）→ 当成「没有快照」，不能让整次登录失败。

### 3.3 角色映射（`rolePermissions`）

| 工作台 `service_role` | 清流权限 |
| --- | --- |
| `admin` | 全量（含 `qingliu.admin`、成员管理、充值） |
| `reviewer` | 读、写资料、签发报告、看账单 |
| `sales` | 读、写资料、看账单、充值 |
| `enterprise_member_full` | 读、写资料、签发报告、看账单 |
| `enterprise_member_basic` | 读、写资料、看账单 |
| `enterprise_member_readonly` | **只读**（读资料 + 看账单） |
| `enterprise_admin` | 同 `admin` |
| 认不出的角色 | 按 `readonly` 处理（**不再降级成 sales**） |

`ql_users.role` 现在只是「默认值 / 显示标签」，由 `localRole()` 收敛：

```text
admin / sales / reviewer        → 原样
enterprise_member_readonly      → "reviewer"（显示用）
其余（含空）                     → "readonly"
```

## 4. 上线与迁移

| 项 | 说明 |
| --- | --- |
| 清流迁移 | `server/migrations/004-session-space.sql`（幂等）：`ql_sessions.tenant_id`、`ql_workbench_accounts.permissions`、回填既有会话 |
| 工作台迁移 | `000062`–`000066`；清流依赖工作台先升到 `LatestMigrationVersion` |
| 上线顺序 | **先工作台，再清流**（清流切换空间要调工作台的 `/me/spaces`） |
| 回滚 | 清流回滚后所有会话退回主身份空间（不丢数据）；工作台回滚见各迁移的 down 注释 |

## 5. 跨库造账号的三个必要条件（踩过坑）

把账号从一套工作台搬到另一套时，**只写 `t_user` 是不够的**：

| # | 必须做 | 否则 |
| --- | --- | --- |
| 1 | 写 `t_user`（`account_type=2`、`tenant_id=企业`） | 账号不存在 |
| 2 | 写 `t_user_service`（`qingliu` 与 `workbench` 各一条，`status=1`） | `serviceRoleForUser` 读不到授权 → `ErrServiceScopeMismatch` → **401** |
| 3 | 用 `auth.HashPassword` 生成 `$argon2id` 哈希 | 工作台 `VerifyPassword` **只认 argon2id**，`$2a$`(bcrypt) 一律返回 false → 401 |

另外注意 **`user_id` 不要照搬源库**：两台机器的主键占用不同（测试的 27 号在生产可能是本地 `admin`），直接照搬会撞主键或被 `ON DUPLICATE KEY` 改掉别人的行。让 `user_id` 自增，再按 email 回查新 id。

## 6. 验收

1. `GET /api/spaces` 未登录返回 **401**（不是 500）；登录后返回空间列表且 `current` 只有一个。
2. 个人账号加入企业后能在个人空间与企业空间之间切换，切换后客户列表/余额随之变化，刷新不回到旧空间。
3. 工作台把某人降为 `enterprise_member_readonly` → 该用户重新登录后看不到上传/核对/签发入口，直接调接口得到 403。
4. 从企业移除某人后，他手上的旧 token 再切该空间会被拒绝（空间声明回库校验）。
5. 只读成员尝试签发正式报告返回 403。

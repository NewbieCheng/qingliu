# 终极改造方案：清流瘦身 + 能力归一（P1/P2/P3）

> 目标：**清流只做业务编排与呈现；AI、解析、OCR、计费、账号全部归一到不加班后端。**
> 清流不再写死任何模型参数；不再自己实现后端已有的能力。
> 状态：方案待批 → 批准后按 P1→P2→P3 执行，每期本地测试通过才推。
> 日期：2026-11-21

---

## 一、现状盘点：清流到底重复实现了什么

### 1.1 后端（不加班）已经有的能力

| 能力 | 后端位置 | 说明 |
| --- | --- | --- |
| 文档解析（PDF/CSV→文本） | `internal/aidoc/extract.go` | `Extract()`：pdftotext + 逐页 OCR，带稳定原因码 |
| 失败原因码 | 同上 | `PDF_ENCRYPTED` / `PDF_TOO_MANY_PAGES` / `PDF_TEXT_EMPTY` / `MISSING_PDFTOTEXT` / `PDF_TOOL_TIMEOUT` / `OCR_UNAVAILABLE` |
| OCR（视觉逐页） | `internal/aidoc/ocr.go`、`/v1/ocr` | `TaskPageOCR = "page_ocr"` |
| 文档分析任务 | `internal/aidoc/application.go`（20KB） | 上传→提取→分析→结果，带状态机与预算 |
| 模型调用 | `internal/llmgateway` | Chat + **Responses**，含 reasoning / max_output_tokens / 计费 |
| 解析计价 | `/api/v1/service/billing/parse-pricing` | 运营后台可调，三档（text/ocr/vision） |
| 积分扣费 | `/api/v1/service/billing/charge` | 服务间调用 |
| 账号与鉴权 | `internal/auth` | 登录/刷新/空间/服务登录 |
| 模型上限收敛 | `gateway.go` `applyMaxTokensCap` / `applyModelMaxOutputTokens` | 全局 + 每模型 |

### 1.2 清流自己的重复实现（**这就是要清洗的部分**）

| 清流文件 | 行数 | 重复了什么 | 处置 |
| --- | --- | --- | --- |
| `parser.go` | 963 | **PDF/OCR 解析全链路**：`pdfinfo`/`pdftotext`/`pdftoppm`/`tesseract` | **P2 删除本地工具调用**，改调后端 aidoc |
| `ocr_writeback.go` | 182 | 逐页 OCR 回写 | **P2 删除**，用 aidoc `page_ocr` |
| `ai_classify.go` | 212 | `documentProbe()` 自己 pdfinfo/pdftotext 探测加密/页数 | **P2 收敛**，改读后端返回的 `ExtractErrorCode`/`Pages` |
| `ai_adopt.go` | 184 | 采纳 AI 结果的状态机 | **P3 合并**进 worker |
| `pricing.go` | 171 | 本地计价缓存 + 扣费编排 | **P3 收敛**为薄封装（只读后端） |
| `structure_rescue.go` | 240 | Chat 调用（将被 Responses 取代） | **P1 迁移** |
| `wb_stream.go` | 284 | Chat 流式 | **P1 迁移** |

### 1.3 清流必须保留的（业务域，后端没有）

| 文件 | 保留理由 |
| --- | --- |
| `domain.go` | 流水领域规则：分类/去重/关联名单/利息排除（Q01/D01/R01…）——这是清流的核心价值 |
| `report.go` | 底稿报告生成 |
| `worker.go` / `pool.go` / `job_policy.go` | 任务队列与准入（清流自己的并发模型） |
| `store.go` | QLGO1 加密存储 + MySQL |
| `spaces.go` / `permissions.go` / `admin_members.go` | **客户授权**（不是账号体系，是业务权限） |
| `audit.go` / `service_audit.go` | 业务审计 |
| `form_template.go` | 增值税申报表栏次模板（业务知识） |
| `parse_pipeline.go` | 五层编排（业务编排） |
| `ai_verdict.go` / `ai_explain.go` | 判决与导诊（业务语义） |

### 1.4 结论

> 清流的 `parser.go`（963 行）+ `ocr_writeback.go`（182）+ `ai_classify.go` 的 probe 部分 ≈ **1150 行重复实现**。
> 这些删掉后，清流后端从 7000+ 行降到约 5800 行，**且解析行为与后端完全一致**（同一套原因码、同一套 OCR）。

## 二、三条铁律（所有改造必须遵守）

| # | 铁律 | 含义 |
| --- | --- | --- |
| **L1** | 清流**不写死任何模型参数** | token 上限、思考强度、模型名、超时全部来自后端或环境变量；代码里不出现魔法数字 |
| **L2** | 清流**不重复实现后端已有能力** | 解析/OCR/AI/计费/账号一律调后端；清流只保留业务域逻辑 |
| **L3** | 失败原因**只翻译不发明** | 用户看到的错误必须能映射到后端的稳定原因码，便于排障 |

## 三、P1：参数归一 + Responses 迁移 + 前端按钮（**本期执行**）

### 3.1 后端（不加班）

| 改动 | 文件 | 说明 |
| --- | --- | --- |
| Responses 嵌套 `reasoning` | `internal/llmwire/openai_responses.go` | 扁平的 `reasoning_effort` → `{"reasoning":{"effort":"none"}}` |
| `off → none` 规范化 | `internal/llmwire/reasoning.go` | `off` 语义修正为"真正关闭" |
| 上限封顶 | `internal/llmgateway/gateway.go` | `MaxTokensCap` 32768 → **393216**（保险丝，不再是业务限制） |
| 模型上限不压低 | 同上 + 迁移 | `auto.max_output_tokens` 30000 → 模型真实上限 |
| 解析服务额度放宽 | `settings.go` + 迁移 | `daily_tokens=0`（不限） |

### 3.2 清流：参数全部去掉写死值

**核心原则：清流不再声明"要多少 token"，只说"给我解析结果"，上限由后端收敛。**

```go
// 改造前（写死 + 一路调）
"max_tokens": 1500 → 4000 → 8000 → 12000

// 改造后（不写 token 上限，交给后端）
"max_output_tokens": wbMaxOutputTokens()  // 读后端配置；读不到才用官方最大值 393216
"reasoning": Object{"effort": wbReasoningEffort()}  // 读后端配置；默认 "none"
```

新增 `server/wb_limits.go`：
- 启动时向 `/api/v1/models` 拉一次模型能力（含 `max_output_tokens`、`reasoning_efforts`）
- 缓存 5 分钟；读不到才用官方常量兜底
- **代码里不再出现任何模型相关魔法数字**

### 3.3 清流：调用点迁移 Responses

| 文件 | 改动 |
| --- | --- |
| `structure_rescue.go` | `POST /v1/chat/completions` → `POST /v1/responses` |
| `wb_stream.go` | 同上；SSE 结束判断 `[DONE]` → `response.completed` |

**请求/响应映射**见 `docs/技术方案-Responses迁移与上限放开.md` §C1。

### 3.4 前端：按钮与交互改造

## 四、P2：解析能力归一（删除本地 poppler/tesseract）

### 4.1 目标

清流**不再安装/调用** poppler、tesseract。解析一律走后端 aidoc。

### 4.2 改动

| 清流文件 | 动作 |
| --- | --- |
| `parser.go` | **重写**：只做「上传→调 aidoc→拿 text/pages/原因码→交给业务层」，删除所有 `exec.Command` |
| `ocr_writeback.go` | **删除**；用 aidoc `page_ocr` |
| `ai_classify.go` | 删除 `documentProbe()` 的 pdfinfo/pdftotext；改读后端 `ExtractStatus`/`ExtractErrorCode` |
| `pricing.go` | 档位判定改由后端返回（text/ocr/vision 由 aidoc 告知），清流不猜 |

### 4.3 收益

- 生产机不再依赖 poppler/tesseract（少一类故障源）
- 加密件/扫描件/超页数用**后端同一套原因码**，前端提示统一
- 清流少 ~1150 行

### 4.4 风险与回滚

| 风险 | 处置 |
| --- | --- |
| aidoc 有页数上限（`maxPages`） | 上线前确认生产配置值；清流按后端返回的 `PDF_TOO_MANY_PAGES` 给提示 |
| 大文件传输耗时 | 后端读取本地路径 or 走 multipart；优先同机直读 |
| 回滚 | 保留旧 `parser.go` 一版（`parser_legacy.go` + build tag），可切回 |

## 五、P3：计费、鉴权、审计归一

### 5.1 计费

| 现状 | 改为 |
| --- | --- |
| 清流本地 `parsePricingCache` + 自己算档位 + 调 charge | 调后端 `POST /v1/parse`（后端内部完成解析+计价+扣费），清流只展示结果与账单 |
| 清流 `pointBalance()` 自己读余额 | 保留读取（展示用），但**扣费判定交给后端**（402 由后端返回） |

### 5.2 鉴权

- 清流现在自己做 session + CSRF + 业务权限。
- 改为：**账号与会话由后端签发**，清流只校验 token + 维护客户授权表（业务权限）。
- 删除 `spaces.go` 中与后端重复的空间/角色逻辑，只留客户授权。

### 5.3 审计

- 统一发到后端的审计通道，清流不再维护双份。

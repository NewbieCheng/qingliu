# 11 · 工作台后台（清流依赖）

清流不是完全孤立系统：登录、套餐、支付订单、积分余额都依赖工作台后台。本文只做交接索引，**后台源码不在本仓库**。

## 2. 两套生产后台

| 域名 | 主机 | 目录 | 说明 |
| --- | --- | --- | --- |
| `worker.no996ai.cn` | 118.196.106.85 | `/opt/no996-backend` | 清流 `WORKBENCH_BASE_URL` 当前指向这套 |
| `worker.bujiaban.top` | 115.191.68.41 | `/opt/no996-backend` | 与清流同机；套餐规划页在这套也可访问 |

两套库独立。清流的登录/订单/余额走 118；如果只更新 115，清流页面可能仍是旧数据。改 `WORKBENCH_BASE_URL` 必须同步核对 SKU、迁移版本和微信支付配置。

## 3. 清流依赖的接口

- `POST /api/v1/service/auth/login`：`service_code=qingliu`，返回 access/refresh token 和 `user.service_role`
- `POST /api/v1/auth/refresh`
- `GET /api/v1/payment/skus?service_code=qingliu`
- `POST /api/v1/payment/orders`
- `GET /api/v1/payment/orders` / `.../{order_no}`
- `GET /api/v1/payment/balance` / `ledgers`

清流后端在 `server/workbench.go` 里封装，浏览器不接触 service secret。

## 4. 套餐与支付

- 套餐规划唯一入口：后台 → 平台 → 套餐规划
- SKU：`ql-monthly-99`（qingliu）、`monthly-99-workbench`（workbench）
- 订单表：`t_payment_order`，二维码字段 `code_url`
- TTL：`PAYMENT_ORDER_TTL` 默认 30m，微信 `time_expire` 同值
- 后台每分钟关闭过期 pending；只清理 closed/failed，paid 永久保留
- 详见 `docs/06-支付与套餐.md`

## 5. 部署

后台有自己的发布流程，**不要从清流仓库直接改后台生产**：

```bash
cd 不加班智能团后端
go test ./...
go build ./cmd/server
# 前端后台
cd web/admin && npm ci && npm run build
```

118 使用仓库脚本 `scripts/_remote-deploy-code-only.sh`；115 需要手工备份、上传、迁移、重启。发布前核对：

```sql
SELECT MAX(version) FROM schema_migrations;
SELECT code,service_code,amount_fen,active FROM t_payment_sku;
```

后台服务端口 7720，健康检查 `/health/ready`。

## 6. 模型

清流 AI 文档分析不单独配置模型；调用工作台网关的默认 chat/vision 模型。后台「AI 能力」页是模型配置唯一入口，已移除重复的 AI 文档模型设置。

## 7. 交接注意

- 后台和服务器的密码/微信商户参数在后台生产环境文件，不在清流 `.secrets`。
- 不要在两套库之间直接复制订单；订单属于实际支付环境。
- 后台管理页与清流站点共用 115 Nginx，但站点配置独立，不要改错 server block。
- 后台发布后要同时验证清流登录和充值页，避免 service secret/接口变更导致清流 401/503。

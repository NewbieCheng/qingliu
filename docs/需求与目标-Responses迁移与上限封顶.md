## 四、为什么要这么改（一句话说清旧方案的死结）

旧链路有三个"漏斗"，每一层都会把输出砍小：

```
qingliu 写死 max_tokens（1500 → 4000 → 8000 → 12000，一路调）
        ↓
工作台 全局 max_tokens_cap = 32768        ← 平台侧收敛
        ↓
工作台 模型 max_output_tokens = 30000（auto）  ← 再收敛一次
        ↓
DeepSeek：reasoning_effort "off" 其实只是"不转发这个参数"
        → 上游认为"未指定" → 默认开启思考
        → 思考 token 和正文共享同一个预算 → 正文被吃光
```

**结论：不是数值调得不够大，是这套参数体系本身没有意义。** 所以要废掉，不是再调一次。

## 七、你的决策点（我等你确认）

1. **`max_output_tokens` 取值**：
   - 方案 A（推荐）：显式写 **393216**（官方最大），让上游自己决定实际能出多少。
   - 方案 B：不传，让上游用默认（思考 64K / 非思考 8K）——但这会**重新引入截断**，与你要求冲突。
   - **我建议 A。**

2. **思考模式默认值**：
   - 方案 A（推荐）：解析链路统一 `effort: "none"`（关闭思考），又快又不会被思考吃预算。
   - 方案 B：保留思考但给满预算（更慢更贵，但复杂推理可能更准）。
   - **我建议 A，且可通过环境变量单独开关。**

3. **后端 `max_tokens_cap` 怎么处理**：
   - 方案 A（推荐）：**保留字段但设为 65535 以上或直接不生效**，仅作为"防打爆"保险丝，不再作为业务限制。
   - 方案 B：彻底删字段（会影响其他调用方与管理后台）。
   - **我建议 A。**

# 13 · 代码结构与工程规范

> **写功能 / 上生产前读** · 与 [AGENTS.md](../AGENTS.md)、[计划-清流减负与AI赋能总册](计划-清流减负与AI赋能总册.md) 配套。  
> 本文回答两件事：① 为什么现在「看代码很累」；② 以后按什么目录和拆分规矩做，避免再堆成一坨。

---

## 0. 给老板 / 决策者（可直接转发）

### 0.1 总册与工程规范怎么分工？

总册主体已验收，现为**短摘要**（三原则 / DoD / 落点）。日常改代码以本文目录规矩 + `01`/`02`/`12` 为准；不要再把总册当施工长文展开。

| 场景 | 实际情况 |
| --- | --- |
| 内部 2～3 人顺路测 | 弱网、老浏览器、插图过重 Word、百页视觉假死等**大多碰不到** |
| 上生产、多业务员并发 | 门闩 / 文件分类 / 按 kind 超时 / busy 减负必须留住；行为变更写进活文档 |

### 0.2 为什么现在改起来特别吃力？

清流有一段历史是**从其他语言 / 形态迁过来**的。迁完功能能跑，但常见后遗症是：

- 一个文件里塞页面 + 请求 + 解析 + 文案 + 状态，**可读性差**
- 组件 / 工具没有二次包装、边界不清，改一处怕牵一片
- 后端个别文件过大（如路由与处理挤在一起），新人接手成本高

这不是「程序员矫情」，而是**后续每个需求都会更贵**的信号。规范目录 + 强制拆分，是为了：

1. 新功能有地方可挂，不继续堆巨石文件  
2. 出问题能定位到「预检 / 分类 / 本机解析 / 加强解析 / 进度」某一层  
3. 人接手、联调、验收时间可控  

建议决策口径：**功能迭代与结构还债并行**——顺手把触达的巨石文件拆到规范目录，不单独开无业务的「大重构月」，但**禁止再往巨石里堆新逻辑**。

## 1. 目标目录（前端）

硬分层（已有机检 `pnpm check:arch`）：

```text
frontend/src/
  main.jsx                 只挂载
  app/                     总装、routes、登录守卫、queries（key/TTL）
  pages/<name>/            页面组合：拼 feature，不写 fetch、不堆业务算法
  features/<domain>/
    api.js                 本域接口（经 shared/api/client）
    constants.js           文案/枚举（金额日期等公共的仍放 shared/lib）
    components/            只负责展示与交互组装
    hooks/                 本域状态与副作用
    lib/                   纯函数：预检、分类、解析、映射（可单测）
    index.js               对外唯一出口（跨 feature 只许引这里）
  shared/
    api/                   client / cache / ApiError（唯一 HTTP 出口）
    ui/                    按钮、弹窗、表单、UploadDropzone…
    lib/                   format、权限展示名等跨域纯函数
    layout/                Shell、导航
    styles/                tokens 与全局样式
```

**依赖方向只能向下**：`app → pages → features → shared`。  
`shared` **禁止** import `features` / `pages`。

### 1.1 新能力往哪挂（解析瀑布）

| 能力 | 建议路径 | 说明 |
| --- | --- | --- |
| 业务预检 | `features/case/lib/upload-preflight.js` | 坏文件当场拒 |
| 一级环境 / 二级 classify | `features/case/lib/client-capability.js` | 门闩 + class，不上屏技术词 |
| 本机 CSV/XLSX/docx | `features/case/lib/parse-*.js`、`docx-table.js`、`docx-media-probe.js`、`client-parse.js` | 纯函数 + 单测 |
| 上传步进 UI | `features/case/components/steps/UploadStep.jsx` | 只调 lib，不写解析细节 |
| 进度文案 | `features/case/constants.js` 或 `lib/parse-copy.js` | 「正在帮你解析 / 加强解析」 |
| AI 面板 | `features/ai-analysis/*` | 与 case 通过 public index 交互 |

## 2. 目标目录（后端 Go）

保持**单进程包 main**，但文件按职责切开，避免继续涨 `main.go`：

| 文件 / 方向 | 职责 |
| --- | --- |
| `main.go` | 启动、配置、`mux()` 路由表（尽量薄） |
| `store.go` | DB / Vault / 事务 |
| `domain.go` | 金额、方向、期间等纯规则 |
| `parser.go`（可再拆） | 服务端拆表；大了按 `parser_csv.go` / `parser_pdf.go` 拆 |
| `worker.go` | 队列、心跳、stall、cancel |
| `workbench.go` | 工作台代理 |
| `ai_analysis.go` / `aidoc` 对接 | AI / 长任务 |
| `*_test.go` | 与文件同目录 |

原则：**路由只注册；业务进具名函数；解析/计费/权限不进 HTTP 回调闭包里写长文。**

## 3. 拆分规矩（什么时候必须拆）

满足任一，就必须拆文件 / 抽模块，禁止「再加 50 行凑合」：

1. 单文件 **> ~400 行** 且仍在加功能  
2. 同一文件里同时出现 **UI + 网络 + 解析算法**  
3. 一段逻辑要被 **≥2 个页面/步骤** 复用  
4. 需要 **单测** 的规则（金额、aliases、classify、预检）却埋在 JSX/handler 里  
5. 出现「复制一段改一处忘改另一处」

### 3.1 二次包装清单（优先做）

| 类型 | 要包装成什么 | 不要 |
| --- | --- | --- |
| HTTP | feature `api.js` + `shared/api/client` | 页面里手写 `fetch` |
| 上传控件 | `shared/ui/UploadDropzone` + step 组装 | 每页自造拖拽区 |
| 解析 | `lib/client-parse` + `classifyFile` | UploadStep 里内联 200 行 |
| 进度 | 一小段 `setFileProgress` / hook | 到处拼字符串 |
| 金额日期 | `shared/lib/format` | 组件内 `toFixed` 各写各的 |
| 权限 | `q.can` / 前端快照 | `role === "admin"` |

## 4. 命名与可读性

- 文件名：前端 `kebab` 或已有风格保持一致；Go 文件 `snake` 职责名。  
- 导出：feature 对外只从 `index.js` 导出；内部相对路径。  
- 注释：只写「为什么 / 不变量」；不写复述代码。  
- 用户文案：集中常量；**禁止**把「前端/后端/class 名」渲到界面。  
- 新依赖：前端必须在 PR/交付说明写理由（AGENTS 硬约束）。

---

## 5. 和验收摘要怎么配合（避免两张皮）

1. **行为变更写活文档**：`01`/`02`/`12` + 必要时更新总册摘要落点表。  
2. **落地时按目录挂文件**：不要把 classify / 解析塞进现有巨型 JSX。  
3. **改到哪拆到哪**：触达 Upload / AI 时顺手剥 lib；不做无关大搬迁。  
4. **验收**：相关单测 + `pnpm check` / `go test`；架构检查红了先修边界。

---

## 6. 自检清单（开 PR / 交活前）

- [ ] 新逻辑落在对的层（lib / components / api），无 pages 直连 client  
- [ ] 无新增「巨石文件」；触达旧巨石已剥一层或注明下轮  
- [ ] 用户可见文案无前后端技术词  
- [ ] 既有行为未偷懒省略：单文件预算、classify、标准 PDF 成功路径、media_heavy、按 kind 超时  
- [ ] `pnpm check`（或至少 arch + 相关单测）与触及的 `go test` 通过

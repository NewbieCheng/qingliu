# 13 · AI 开发规范（交给 AI 的开工前必读）

> **使用方式**：把本文件**整段**贴给要接手开发的 AI（或放进它的 system prompt / AGENTS.md）。
> 规则是**硬约束**，不是建议。AI 开工前必须读完，并先输出「我理解的项目边界 + 本次要改的文件清单」，等确认后再动手。
> 本文以外，`AGENTS.md`、`README.md`、`docs/00-项目总览.md` 为并列必读。

---

## 一、这是什么项目（先认清，再改代码）

清流 Qingliu：面向业务员 / 复核员 / 管理员的**内部客户资料与流水初筛工作台**。

- 它不是银行审批系统，**不做**贷款资格结论，报告仅供内部初筛。
- 它是**单体应用**：一个 Go 二进制，同时提供 API + React 静态文件；没有 Node 常驻进程、没有第二个服务。
- 登录 / 计费 / 支付订单**全部通过工作台后台**（另一个仓库，不在本仓库），本仓库只做代理和界面。

## 二、技术栈（统一，不准换）

| 层 | 选型 | 硬性要求 |
| --- | --- | --- |
| 前端 | React 19 + Vite 7，原生 CSS | **不引入** UI 框架、路由库、状态库、请求库 |
| 前端语言 | JavaScript（`.js` / `.jsx`，ESM） | 不上 TypeScript，不加大型依赖 |
| 后端 | Go 1.26，标准库 `net/http` | **不用** Web 框架，**不用** ORM |
| 数据库 | MySQL 8，库名 `qingliu`，表前缀 `ql_` | 不与工作台共用表 |
| 后台任务 | Go 进程内单执行器（`worker.go`） | 不引入 Redis / 消息队列 / 第二个常驻服务 |
| 文件 | `DATA_DIR` 落盘，QLGO1（AES-256-GCM，`VAULT_KEY`） | 必须走 Store 读写，不准自己 `os.WriteFile` |

新增依赖前必须说明理由；除上表列出的库（`mysql`、`fpdf`、`excelize`、`x/crypto`、`x/text`、`qrcode`）外，默认**不加**。

## 三、目录结构与依赖方向（强约束）

```text
qingliu-workspace/
├── frontend/
│   ├── src/
│   │   ├── main.jsx        只挂载 React，不写业务
│   │   ├── app/            总装、routes.jsx、登录守卫、ErrorBoundary、queries/
│   │   ├── pages/          页面组合：login clients case recharge profile admin not-found
│   │   ├── features/       业务域：auth clients case billing ai-analysis profile admin
│   │   │   └── <domain>/   api.js · index.js · components/ · constants.js · hooks/ · lib/
│   │   └── shared/         api/ router/ layout/ ui/ hooks/ lib/ styles/（公共能力）
│   ├── scripts/            check-architecture.mjs（架构边界检查）、smoke.mjs（浏览器冒烟）
│   └── dist/               交付产物：改源码后必须重新 build，禁止只改 dist
├── server/                 Go 单包 main
│   ├── main.go             路由、中间件、启动、配置
│   ├── store.go            MySQL Store、查询、事务、加锁、加密文件读写
│   ├── domain.go           业务规则 / 金额 / 期间 / 统计
│   ├── parser.go           CSV/XLSX/PDF/OCR 解析
│   ├── report.go           PDF / Excel / HTML 报告
│   ├── ai_analysis.go      AI 文档分析
│   ├── workbench.go        工作台 service login / 计费代理
│   ├── worker.go           进程内单执行器
│   ├── schema.sql          CREATE TABLE IF NOT EXISTS 启动建表
│   └── migrations/         版本化迁移 SQL（001-…、002-…）
├── deploy/                 构建、启动、Nginx 示例
└── docs/                   交接文档（本文件在 13）
```

**前端依赖方向只能从上到下**：`app → pages → features → shared`。

| 规则 | 违反后果 |
| --- | --- |
| `shared` 不得 import `features` / `pages` | `npm run check:arch` 直接失败 |
| `pages` 不得 `fetch`，也不得直接 import `shared/api/client.js` | 同上 |
| 同一 feature 内部用**相对路径**（`./components/X.jsx`） | 同上 |
| 跨 feature 只能 import 对方 `@/features/<name>/index.js` | 同上 |
| 内部跳转只能用 `navigate()` / `<Link>`，禁止 `window.location.href =` | 同上（会整页刷新） |
| 后端不分层目录，按职责单文件；**新增业务代码放已有文件的对应位置**，不要自建 package 目录 | code review 驳回 |

## 四、前端必守规则（逐条）

1. **请求链路唯一**：`page → feature/api.js → shared/api/client.js → 后端`。
   - CSRF、401 跳登录、超时、`ApiError`、网络错误文案**只**在 `shared/api/client.js` 处理。
   - 新增接口 = 在对应 feature 的 `api.js` 加一个函数，不要写到组件里。
2. **查询缓存唯一入口**：`app/queries/index.js` 定义 key + TTL；缓存原语只在 `shared/api/cache.js`。
   - 列表**必须服务端分页**（`page` 参数），不准前端拉全量再切。
   - 写操作成功后**先失效相关缓存再刷新**；退出登录 / 401 必须清空全部缓存。
   - 缓存只放内存，禁止写 `localStorage` / `sessionStorage`；资金、权限、报告签发**不得**依赖缓存判断。
3. **页面只做组合**：`pages/<name>/XxxPage.jsx` 负责拼装，业务逻辑下沉到 feature。
   底稿四步走 `?step=` URL，新功能加到对应 step/feature，**不要堆回 `CasePage`**。
4. **样式**：颜色、字体、间距优先用 `shared/styles/tokens.css`；保留深松绿 / 账本纸的设计语言；不引入 CSS 框架、不写内联魔法值。
5. **文案与格式化**：金额、日期、角色名、状态文案只在 `shared/lib/format.js` 或 feature `constants.js` 定义一次。
6. **图标**：统一 `shared/ui/icons.jsx`，不要用字符拼图标。
7. **提示**：成功 / 失败统一走 `shared/ui/toast-api.js` 的 `toast()`；不要恢复表单内绿/红提示条。
8. **新增页面的固定动作**：`pages/<name>/` → 必要时 `features/<domain>/` → `app/routes.jsx` 注册 → 按需改 `shared/layout/navigation.js`。
9. **响应式**：390px 宽度不得横向溢出（smoke 会检查）。

## 五、后端必守规则（逐条）

1. **路由**：只在 `main.go` 的 `mux()` 内 `m.HandleFunc("METHOD /api/...", a.route(...))`，Go 1.22+ 方法与路径变量写法（`{cid}`、`{tid}`）。
2. **中间件顺序不要动**：`a.route()` 统一处理 panic→JSON、安全头（CSP/HSTS/no-store）、并发槽位（`slots`，满则 503）、`MaxBytesReader`、会话 Cookie `ql_session`、非公开接口 401、写请求 Origin 校验 + `X-CSRF-Token` 校验。**新增接口自动继承**，不要在 handler 里重复实现。
3. **错误抛出**：用 `bad(code, "中文可读提示")` / `require(cond, msg)`，不要 `http.Error` 或裸 500。
   - 客户端提示语面向业务员，**不要暴露 SQL、路径、堆栈**。
4. **权限**：客户级接口一律 `q.access()`（无权限**返回 404 而不是 403**，避免探测）；管理接口 `q.admin()`；写客户数据走 `q.edit()`（分布式锁 + 有后台任务时 409）。
5. **数据访问**：全部经 `Store`（`exec` / `query` / `one` / `lock` / `event` / `write` / `read`），不要在 handler 里直接用 `db.Query`。
   - 参数永远用占位符 `?`，**禁止字符串拼接 SQL**。
6. **字段与 JSON**：请求体经 `q.body()`（`UseNumber`，拒绝尾随内容）；返回 `q.json(...)`（`browserJSON` 规范化）。数据库字段与前端字段命名保持一致，改动必须前后端同步。
7. **审计**：关键写操作调用 `s.event(user, cid, action, detail)` 写 `ql_events`；操作记录查询走 `GET /api/admin/audit`（支持分页 + 筛选），**不要**在 `/api/admin` 里附带全量事件。
8. **后台任务**：长任务投递到 `worker.go`（`ql_jobs`），不阻塞 HTTP；不能用 goroutine 裸跑无记录的任务。任务需写进度（`jobProgress`），重启可恢复。
9. **文件**：原始资料 / 报告落盘必须走 `Store.write` / `Store.read`（带 `VAULT_KEY` 加密）；数据库只存索引、元数据、加密后的路径。
10. **报告**：PDF/Excel/HTML 由 Go 生成；正式报告是**快照**，后续资料变化不覆盖已签发报告。
11. **数据库变更**：
    - `schema.sql` 是 `CREATE TABLE IF NOT EXISTS`，**只能给新库建表**。
    - 给已有表加索引 / 字段：在 `server/migrations/` 新建按版本命名的 SQL（如 `003-xxx.sql`），更新 `migrations/README.md` 的上线顺序，**人工确认后**执行，执行前备份。
    - 禁止直接改线上表而不回写迁移文件。

## 六、前后端能不能分离？（明确回答）

| 问题 | 回答 |
| --- | --- |
| 前后端是否解耦 | **逻辑上解耦，部署上不分家**。前端只通过 `/api/*` 同源 JSON 通信，没有共享代码、没有服务端渲染依赖。 |
| 能不能拆成两个仓库 / 两个进程 | **能，但默认不做**。前端是纯静态产物，任意静态服务器 + 反向代理 `/api` 即可跑起来；后端无任何前端耦合。 |
| 为什么现在不拆 | 同源带来 Cookie、CSRF（`X-CSRF-Token`）、CSP `default-src 'self'` 的零配置安全；拆开后必须重新配置 CORS、`credentials: include`、Cookie SameSite/Secure、`Origin` 白名单（后端写请求会校验 `Origin`）。 |
| 拆分时 AI 必须改哪里 | 前端 `vite.config.js` 的 proxy、`shared/api/client.js` 的 baseURL 与 `credentials`；后端 `PUBLIC_ORIGIN`、Origin 校验白名单、Cookie 域。**且必须由人确认**。 |
| 拆分后仍然不变 | `api()` 单一通道、`ApiError` 语义、`ql_session` + CSRF 机制、接口契约（字段名 / 状态码 / 错误结构 `{error}`）。 |

结论：**AI 默认按单体同源开发**，除非业主明确要求拆分。

## 七、环境（务必分清，写错会读到错的库）

| 环境 | 前端 | 工作台后端（`WORKBENCH_BASE_URL`） | 服务器 | 数据库 |
| --- | --- | --- | --- | --- |
| 生产 | `qingliu.bujiaban.top` | `worker.bujiaban.top` | 115.191.68.41 | 独立 `qingliu` + `intelligent_team` |
| 测试 | 未部署 | `worker.no996ai.cn` | 118.196.106.85 | 另一套独立库 |

- `bujiaban.top` = 生产，`no996ai.cn` = 测试；两套 MySQL 完全独立，**禁止交叉指向**。
- 切换 `WORKBENCH_BASE_URL` 后必须重新登录（旧 token 属于旧库）。
- 所有密钥、服务器账号、`VAULT_KEY` 只在 `.secrets/` 或密码管理器：**不得**写进代码、README、提交记录、截图、日志。

## 八、本地开发与验证（改动后必跑的最小集）

```bash
# 前端（5173，/api 直接代理到生产，不需要本地 MySQL / Go）
cd frontend && npm install && npm run dev

# 前端检查：ESLint → 架构边界 → Vitest → 构建
cd frontend && npm run check

# 涉及路由 / 登录 / 底稿流程时
cd frontend && npm run smoke

# 后端（Windows 下把缓存指到工作区内）
cd server && GOCACHE=$PWD/.gocache GOTMPDIR=$PWD/.gotmp go test ./... && go vet ./...
```

- 改完**至少**跑与该改动对应的检查；全绿才算完成。
- 无法验证（如无测试环境）必须在回复里**明确说明未验证**，不得声称已验证。
- `frontend/dist` 是交付产物：改前端源码后必须 `npm run build`，不能只改 dist。
- `bin/` 是本机构建产物，不提交。

## 九、禁止事项（红线）

1. ❌ 在清流里另建账号 / 支付 / 订单库，或绕开工作台直接改计费。
2. ❌ 引入 Redis、消息队列、第二个常驻服务、Docker 生产部署。
3. ❌ 恢复单文件大组件；把业务逻辑塞回 `pages`。
4. ❌ 页面直接 `fetch` / 直接 import `shared/api/client.js`。
5. ❌ 前端缓存写入 localStorage / 用它做资金或权限的最终判断。
6. ❌ 用字符串拼接 SQL；在 handler 里绕过 Store 直接写文件。
7. ❌ 把真实密钥、服务器密码、客户资料写进代码或提交。
8. ❌ 自动 `git commit` / `push` / 部署生产——**除非业主明确说“上线 / 发布 / 部署”**。
9. ❌ 提交 `node_modules`、`dist` 的无关改动、`.env.local`、`.secrets/`。
10. ❌ 未经确认改接口字段名、状态码、Cookie/CSRF 机制（会同时打破前后端契约）。

## 十、AI 的开工流程（照做）

1. **读**：本文件 → `AGENTS.md` → `README.md` → `docs/00-项目总览.md`（涉及部署再读 `docs/05`）。
2. **定位**：先查代码图 / 搜索定位符号与调用链，不熟悉的仓库先建索引；不要凭猜改文件。
3. **复述**：用 3–5 行输出「需求理解 + 环境（生产/测试）+ 拟改文件清单 + 是否触碰红线」，**等业主确认**。
4. **最小改动**：只改点名的地方，不顺手重构、不补无关测试、不改无关文档。
5. **自检**：跑第八节对应检查；架构检查失败必须先修边界问题。
6. **交付说明**：改了哪些文件、为什么、怎么验证的、哪些没验证。

## 十一、新增一个功能的标准动作（模板，照着做）

以「客户列表增加导出按钮」为例：

```text
1. 后端  server/main.go      加路由 GET /api/clients/export → a.route(...)，内部调 Store
2. 后端  server/store.go     加查询函数（占位符、分页）
3. 后端  server/audit.go     写操作 s.event(...) 记录
4. 前端  features/clients/api.js        加 exportClients()
5. 前端  app/queries/index.js           如需缓存，定义 key + TTL（写操作后调 invalidateClients）
6. 前端  features/clients/components/Xxx.jsx   纯展示/交互
7. 前端  pages/clients/ClientsPage.jsx   组合，调 feature api
8. 前端  features/clients/index.js       export 对外导出
9. 验证  npm run check → 必要时 npm run smoke
```

## 十二、一句话总结

> **保持单体、保持同源、保持分层；前后端只通过 `/api` JSON 通信；所有请求走 `client.js`，所有数据走 `Store`，所有变更都要版本化迁移；不新增框架、不新增服务、不动红线；改完必须自检。**

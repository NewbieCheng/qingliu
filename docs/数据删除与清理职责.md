# 数据删除与清理职责

> 说明"删除一个客户档案时，谁删什么、谁不清什么"，避免两套清理逻辑互相打架，也避免留下孤儿文件。

---

## 一、职责划分

| 对象 | 谁清理 | 时机 |
| --- | --- | --- |
| `qingliu` 库内的客户/文档/交易/复核/报告/任务等行 | **清流** | 用户点删除，即时 |
| `/var/lib/qingliu/uploads/<cid>/` 下的原件 | **清流** | 同上，库删成功后 |
| 不加班总后台侧的上传副本、计费流水、审计 | **不加班后端** | 后端自己的定时任务 |

**结论：清流只清自己的数据，不碰总后台。** 两边不冲突——清流删干净后，总后台的定时清理任务扫不到东西自然跳过。

---

## 二、清流删除流程

`DELETE /api/clients/{cid}`（**仅管理员**，后端 `q.admin()` 强校验）

1. 开事务，按依赖顺序删：
   ```
   ql_reviews      （挂在交易行上，先删）
   ql_transactions
   ql_ai_analyses
   ql_documents
   ql_jobs
   ql_reports
   ql_upload_batches
   ql_submissions
   ql_grants
   ql_events
   ql_customers
   ```
2. 提交事务
3. **事务成功之后**才删磁盘原件（`purgeUploads`）
4. 记录审计事件 `delete_customer`

### 为什么先删库、后删文件

反过来做，一旦事务回滚，原件已经没了而库里的记录还在——变成指向空文件的坏记录。宁可留下孤儿文件（有定时清理兜底），也不能留下坏记录。

### 为什么必须删原件

只删库会在 `uploads/<cid>/` 留下永远回收不到的**加密**文件：

- 长期占满磁盘
- 里面是客户的真实流水，档案删了还留着有合规风险

`purgeUploads` 同时清理 `pending/` 下已无对应 job 的中转文件。

---

## 三、单条交易删除

`DELETE /api/clients/{cid}/transactions/{tid}`

- 先删 `ql_reviews` 里该交易的复核记录，再删交易行（同一事务）
- 不动磁盘原件——原件是整份文件的，不是某一行

---

## 四、手工新增交易

`POST /api/clients/{cid}/transactions`

- 走与自动解析**同一套** `standard()` 归一与质检
- 所以手工行的 `quality`/`direction` 与自动解析完全一致，核对规则不需要为"手工行"开特例
- 重复检测复用 `fingerprint`，与原件里抽出来的行一起参与去重
- 未通过校验（日期/金额缺失、方向不明）直接拒绝，不写入脏行

---

## 五、权限

| 操作 | 权限 |
| --- | --- |
| 删除客户档案 | **仅管理员** |
| 删除单条交易 | 有该客户编辑权限即可 |
| 手工新增交易 | 有该客户编辑权限即可 |

管理员判定：前端按 `isQingliuAdmin(user)` 隐藏按钮，后端 `q.admin()` 独立校验。
**不可撤销操作不能只靠前端隐藏**——所以两边都做。

---

## 六、审计

所有删除都会写 `ql_events`：

| action | 含义 |
| --- | --- |
| `delete_customer` | 删除客户档案 |
| `delete_transaction` | 删除单条交易 |
| `add_transaction` | 手工新增交易 |
| `document_reparse` | 重新解析文档 |

审计记录随客户一起被删（`ql_events` 按 `customer_id` 清理），所以删除动作本身的痕迹保留在系统日志里，而不是该客户的事件流里。

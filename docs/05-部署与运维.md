# 05 · 部署与运维

> 真实主机、账号、密钥见 `.secrets/SERVER-INFO.md` 与 `.secrets/DEPLOY-SECRETS.txt`，不提交。本文用 `$QINGLIU_HOST` 占位。

## 1. 拓扑

```text
浏览器 → HTTPS qingliu.bujiaban.top
  └─ Nginx (TLS, 限流, 64MB, 130s)
       └─ 127.0.0.1:8787  qingliu (Go, systemd)
            ├─ MySQL 8  qingliu.*
            ├─ /var/lib/qingliu  加密原件/报告
            └─ HTTPS worker.bujiaban.top  工作台（登录/计费/订单）
```

同机还跑工作台后台（7720）和 MySQL；共用主机/Nginx，不共用数据库、端口或进程。**不使用 Docker。**

## 4. 发布

> **迁移不是可选项**：`schema.sql` 的 `IF NOT EXISTS` 不给已有表补列。漏执行 `server/migrations/` 会让**整站每个带登录态的请求**返回「处理失败，请联系管理员」（2026-11-10 已踩过，缺 005）。应用账号没有 `ALTER`，迁移必须用 root。

```bash
# 1) 备份（会短暂停服，导出 DB + 数据目录）
ssh -i "$QINGLIU_SSH_KEY" root@"$QINGLIU_HOST" /usr/local/sbin/qingliu-backup.sh

# 2) 迁移（按编号顺序、幂等）
scp -i "$QINGLIU_SSH_KEY" server/migrations/*.sql root@"$QINGLIU_HOST":/tmp/qingliu-migrations/
ssh -i "$QINGLIU_SSH_KEY" root@"$QINGLIU_HOST" \
  'for f in /tmp/qingliu-migrations/*.sql; do echo "== $f"; mysql -uroot qingliu < "$f"; done'

# 3) 上传
scp -i "$QINGLIU_SSH_KEY" /tmp/qingliu-release.tar.gz root@"$QINGLIU_HOST":/tmp/

# 4) 替换
ssh -i "$QINGLIU_SSH_KEY" root@"$QINGLIU_HOST" 'bash -s' <<'REMOTE'
set -euo pipefail
TS=$(date -u +%Y%m%d-%H%M%S)
rm -rf /tmp/qingliu-new && mkdir -p /tmp/qingliu-new
tar -xzf /tmp/qingliu-release.tar.gz -C /tmp/qingliu-new
cp /opt/qingliu/qingliu /opt/qingliu/qingliu.bak-$TS
systemctl stop qingliu
install -m 755 /tmp/qingliu-new/bin/qingliu-amd64 /opt/qingliu/qingliu
rsync -a --delete /tmp/qingliu-new/frontend/dist/ /opt/qingliu/frontend/dist/
rsync -a /tmp/qingliu-new/fonts/ /opt/qingliu/fonts/
systemctl start qingliu && sleep 2 && curl -fsS http://127.0.0.1:8787/health
REMOTE
```

> 坑：`ExecStart` 是 `/opt/qingliu/qingliu`，**不是** `.../bin/qingliu-amd64`；只更新后者不生效。静态 SVG 也由 Go 提供，新增根目录资源要检查 `main.go` 的 `.svg` 分支。

**回滚**：`systemctl stop` → 恢复 `qingliu.bak-<TS>` 与对应 `dist` 快照 → 按备份点恢复数据库（结构不兼容时必须先恢复库，不能只回退二进制）→ 启动并 `/health`。`VAULT_KEY` 不变才能解密旧文件。

## 5. Nginx 与数据库

- 80 仅 ACME + 301；443 反代 `127.0.0.1:8787`
- `/api/login` 单独 `limit_req`；`client_max_body_size 64m`；读写超时 130s
- 安全头：HSTS、X-Content-Type-Options、Referrer-Policy、X-Frame-Options
- 业务不缓存；`/assets/` 带哈希长缓存
- 站点配置在服务器 `/etc/nginx/sites-available/qingliu.bujiaban.top.conf`，示例见 `deploy/nginx.conf.example`

```sql
CREATE DATABASE qingliu CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'qingliu'@'localhost' IDENTIFIED BY '...';
GRANT SELECT,INSERT,UPDATE,DELETE,CREATE,INDEX,REFERENCES ON qingliu.* TO 'qingliu'@'localhost';
```

DSN 与口令在 `/etc/qingliu/qingliu.env`（0600）。不要用 root 跑应用。

## 6. 日常检查

```bash
systemctl status qingliu && systemctl status nginx
journalctl -u qingliu -n 100 --no-pager
curl -fsS http://127.0.0.1:8787/health     # {"status":"ok"}
```

## 7. 备份与恢复

`/usr/local/sbin/qingliu-backup.sh` 备份 MySQL `qingliu` + `/var/lib/qingliu` + `VAULT_KEY`，每日 03:30，保留 30 天，脚本会短暂停服。每月至少做一次恢复到临时库/目录的演练。

恢复：停服 → 重建库并导入 `.sql.gz` → 解包数据到 `/var/lib` → `chown -R qingliu:qingliu && chmod 700` → 用**同一恢复点**的 `VAULT_KEY` → 启动并 `/health`。

证书：`certbot certificates`、`certbot renew --dry-run`、`systemctl reload nginx`；确认自动续期钩子仍在。

## 8. 常见故障

| 现象 | 排查 |
| --- | --- |
| `/health` 503 且 `process active` | 先看是「数据库不可用」还是 **`当前服务器繁忙，请稍后重试`**；后者是某一档准入池满了（§12）：日志 `请求被拒：<档> 池已满`，调大对应 `QL_POOL_*` 或查是不是有人狂刷原件页 |
| 带登录态请求全报「处理失败」 | 漏迁移（多为 005/006/007）→ `journalctl` 找 1054 |
| 登录 401 | 工作台 service 账号/密钥、账号停用、本地兜底是否开启 |
| `AUTH_CAPTCHA_REQUIRED` | 前端没带图形验证码，**不是**密码错 |
| 套餐 503 | `WORKBENCH_BASE_URL` 可达性、SKU 是否存在 |
| 二维码不显示 | 订单是否 pending、`code_url` 是否为空、是否过期 |
| 上传 413 | Nginx `client_max_body_size` / 批次限制 |
| 报告 500 | 字体、`DATA_DIR` 权限、`VAULT_KEY`、任务日志 |
| 重启后任务不动 | `ql_jobs` 状态、执行器日志、MySQL 命名锁 |
| 静态资源 404 | 是否在 `dist`、Go 静态分支是否允许该扩展名 |

## 10. 安全事件与待补

安全事件：停用账号/撤销会话 → 保留日志 → 更换泄露凭据（`VAULT_KEY` 不能直接轮换，需先设计重加密）→ 通知负责人。

## 11. 故障档案：2026-11-12 全站 503 假死（wbRefresh gate 泄漏）

**现象**：`systemctl status qingliu` 是 `active (running)`、内存仅 10MB、无重启，但站点打不开；`curl http://127.0.0.1:8787/health` 稳定 `503 {"error":"当前服务器繁忙，请稍后重试"}`，nginx 侧同样 503，`access.log` 全是 503。nginx 配置与证书都没问题，MySQL 也正常（`show processlist` 无长查询）。

**定位**（10 分钟内可复现的手法）：

```bash
curl -s -i http://127.0.0.1:8787/health        # 503 + 「当前服务器繁忙」= 并发槽满，不是 DB 故障
kill -QUIT <MainPID>                           # 打出全部 goroutine 栈；Restart=on-failure 会 5s 后自动拉起
journalctl -u qingliu --no-pager | grep -B2 -A25 'chan receive, [0-9]* minutes'
```

栈里 4 个请求 goroutine 全部停在 `server/workbench.go` 的 `<-gate.done`（当时已卡 196 分钟），正好占满 `main.go` 的 4 个并发槽。

**根因**：工作台 refresh 单飞 gate 的收尾不是 `defer`。`wbRefresh` 先登记 `a.refreshGates[userID] = gate`，再调 `wbRefreshOnce`；一旦这一步 panic（`s.one` / `s.unseal` 遇到 MySQL 错误，日志里表现为 `request failed: *mysql.MySQLError`，被 `route()` 的 recover 吞掉），`delete` + `close(gate.done)` 永远不会执行。此后该用户每个请求都阻塞在 `<-gate.done`，4 个槽被占满 → 全站 503，且只有重启进程能恢复。这不是工作台的问题，也不是 DNS/证书。

**修复**（`server/workbench.go`）：gate 收尾移入 `defer`（`recover()` 后先写 `gate.token/err`、销号、`close(gate.done)`，再按原语义 `panic`）；等待方加 `wbRefreshWaitTimeout = 30s` 兜底，超时直接报「工作台暂时不可用」。回归：`server/workbench_refresh_test.go` + `go vet ./...`。

**当日处置**：`kill -QUIT` 取栈 → `systemctl restart` 恢复访问 → 本地交叉编译 `bin/qingliu-amd64` → `scp` 上传 → 备份旧二进制为 `qingliu.bak-<TS>` → `install -m 755` 替换 `/opt/qingliu/qingliu` → `systemctl start` → 三次 `/health` 均 `{"status":"ok"}`。**只换 Go 二进制，不动 `frontend/dist`、不做 git push**，所以上线范围仅此一处修复。

**遗留**：（已处理，见 §12）并发槽改为按代价分档；`/health` 与静态资源彻底出池。

## 12. 请求准入：分档池（2026-11-12 起的口径）

### 12.1 为什么不再用「全站 4 槽」

`2340d1c`（2026-11-06 初始交付）在 `route()` 上挂了唯一的 `slots: make(chan struct{}, 4)`，本意是给 `pdfPage()` 的 `pdftoppm` 子进程（单页渲染几十 MB）加闸，但闸装在全站唯一入口上，于是：

- 首页 HTML、`/assets/*.js`、`/health` 也要抢这 4 个槽 → **槽满时连页面都打不开**（用户看到的就是「服务器繁忙」，因为 `index.html` 也 503）。
- 满池**立刻** 503，不排队，瞬时并发直接失败。
- 全站唯一的 `MemoryMax=1G` 上限实际上没人碰得到（实测进程峰值 13MB），4 这个数对 JSON 接口毫无意义。

### 12.2 现在的分档

```text
浏览器
  │
  ▼
Nginx (443, keepalive, 130s)
  │
  ▼
route()  ──① 定档（server/pool.go: poolFor）
  │
  ├─ 非 /api/* 且非原件/上传 ──► 不入池 ──► 直接服务
  │     /health · index.html · /assets/* · *.svg
  │     （探活不再被业务拖累；静态资源只是读磁盘）
  │
  ├─ /api/clients/{cid}/original/{did}/{page} ──► render 池 4（排队 2s）
  │     pdftoppm 渲染，唯一真吃内存的同步接口
  │
  ├─ */upload · */upload-parsed ───────────────► bulk 池 2（排队 1s）
  │     单请求最多缓冲 64MB
  │
  ├─ /api/billing/* · /api/spaces* · /api/switch-space · /api/service/* ──► proxy 池 32（排队 300ms）
  │     转发工作台，主要消耗上游等待（客户端超时 15s）
  │
  ├─ 其它 GET/HEAD ───────────────────────────► read 池 64（排队 200ms）
  │     DB 毫秒级
  │
  └─ 其它写请求 ──────────────────────────────► write 池 32（排队 500ms）
        │
        ▼
     满池且排队超时 ──► 503 + Retry-After: 1
                       （日志：请求被拒：<档> 池已满…，10s 节流）
```

档位与默认值（可用环境变量覆盖，写进 `/etc/qingliu/qingliu.env` 后重启生效）：

| 档 | 环境变量 | 默认 | 排队窗口 | 谁在里面 |
|---|---|---|---|---|
| read | `QL_POOL_READ` | 64 | 200ms | `GET /api/**`（除 proxy/render/bulk） |
| write | `QL_POOL_WRITE` | 32 | 500ms | `POST/PUT/DELETE /api/**`（除 proxy/bulk） |
| proxy | `QL_POOL_PROXY` | 32 | 300ms | 转发工作台的接口 |
| bulk | `QL_POOL_BULK` | 2 | 1s | `/upload`、`/upload-parsed` |
| render | `QL_POOL_RENDER` | 4 | 2s | 原件 PDF 页渲染 |
| — | 不入池 | — | — | `/health`、HTML、`/assets/*`、`*.svg` |

设成 `0` 表示关闭该档（该档不再限流）。

### 12.3 容量怎么估

公式：**可长期承载的活跃用户数 ≈ 档容量 ÷（人均每秒占用该档的时间）**

| 场景 | 单请求占档 | 默认档容量下的吞吐 |
|---|---|---|
| 读接口（实测 0.1–2ms） | 2ms | 64 槽 ≈ 32000 req/s，几百到几千活跃用户 |
| 转发工作台（0.3–3s） | 1s | 32 槽 ≈ 32 req/s ≈ 8–30 个同时在充值页的人 |
| 原件页渲染（2–5s） | 3s | 4 槽 ≈ 1.3 req/s（+ 前端预取邻页，约 3 请求/次翻页）→ 约 1–2 人连翻不互相拖累 |
| 上传（64MB 缓冲） | 0.3–2s | 2 槽，多余请求排队 1s 后 503 |

要放大就调大对应档，**不要**再把它们合成一个数。真实数字用 §12.5 的压测脚本量，别拍脑袋。

### 12.4 前端已做的省请求（都会减少占档）

- 内存 TTL 去重：`me` 60s、`balance` 10s、`clients` 10s、`case` 8s（`frontend/src/app/queries/index.js`）。
- 原件页 PNG 存 IndexedDB，二次翻页不发请求（`case/lib/page-preview-cache.js`）。
- 邻页预取 ±1（`case/lib/prefetch-pages.js`）—— 它把 render 档的请求变成「一次翻页 1+2 个」，所以 render 档不能调得太小。
- 静态资源 `immutable` 长缓存，页面 HTML 走 304。

### 12.5 压测与验收

```bash
# 只换二进制后在生产机本地压（不占公网带宽）
bash /tmp/loadtest.sh            # 并发 1/8/32/64 打 /health、/api/me、/api/billing/balance
```

验收：`/health` 在任意并发下 503 率为 0；`/api/me` 在 64 并发下 503 率为 0；`proxy` 档在 32 并发下最多出现排队延迟、不出现 5xx 级联。

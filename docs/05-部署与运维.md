# 05 · 部署与运维

> 真实主机、账号、密钥见 `.secrets/SERVER-INFO.md` 与 `.secrets/DEPLOY-SECRETS.txt`，不提交。本文用 `$QINGLIU_HOST` 占位。

## 1. 拓扑

```text
浏览器 → HTTPS qingliu.bujiaban.top
  └─ Nginx (TLS, 限流, 64MB, 130s)
       └─ 127.0.0.1:8787  qingliu (Go, systemd)
            ├─ MySQL 8  qingliu.*
            ├─ /var/lib/qingliu  加密原件/报告
            └─ HTTPS worker.bujiaban.top  工作台（登录/计费/订单）
```

同机还跑工作台后台（7720）和 MySQL；共用主机/Nginx，不共用数据库、端口或进程。**不使用 Docker。**

## 2. 环境（别弄反）

| 环境 | 域名后缀 | 工作台 | 清流 | 主机 |
|---|---|---|---|---|
| **生产** | `bujiaban.top` | `worker.bujiaban.top` | `qingliu.bujiaban.top` | 115.191.68.41 |
| **测试** | `no996ai.cn` | `worker.no996ai.cn` | 尚未部署 | 118.196.106.85 |

生产 `WORKBENCH_BASE_URL` **必须**是同环境的 `worker.bujiaban.top`；指错就落到测试库。改地址后必须重新登录（旧 token 属于旧库）。

## 3. 构建与打包

```bash
bash deploy/build.sh     # pnpm build + go test/vet + linux amd64/arm64 交叉编译
```

产出 `bin/qingliu-amd64`、`bin/qingliu-arm64`、`frontend/dist`。构建失败不要发布。

```bash
tar -czf /tmp/qingliu-release.tar.gz \
  bin/qingliu-amd64 frontend/dist fonts deploy docs licenses samples \
  README.md THIRD_PARTY_NOTICES.md
```

不要带 `.secrets`、`.env`、客户资料。

## 4. 发布

> **迁移不是可选项**：`schema.sql` 的 `IF NOT EXISTS` 不给已有表补列。漏执行 `server/migrations/` 会让**整站每个带登录态的请求**返回「处理失败，请联系管理员」（2026-11-10 已踩过，缺 005）。应用账号没有 `ALTER`，迁移必须用 root。

```bash
# 1) 备份（会短暂停服，导出 DB + 数据目录）
ssh -i "$QINGLIU_SSH_KEY" root@"$QINGLIU_HOST" /usr/local/sbin/qingliu-backup.sh

# 2) 迁移（按编号顺序、幂等）
scp -i "$QINGLIU_SSH_KEY" server/migrations/*.sql root@"$QINGLIU_HOST":/tmp/qingliu-migrations/
ssh -i "$QINGLIU_SSH_KEY" root@"$QINGLIU_HOST" \
  'for f in /tmp/qingliu-migrations/*.sql; do echo "== $f"; mysql -uroot qingliu < "$f"; done'

# 3) 上传
scp -i "$QINGLIU_SSH_KEY" /tmp/qingliu-release.tar.gz root@"$QINGLIU_HOST":/tmp/

# 4) 替换
ssh -i "$QINGLIU_SSH_KEY" root@"$QINGLIU_HOST" 'bash -s' <<'REMOTE'
set -euo pipefail
TS=$(date -u +%Y%m%d-%H%M%S)
rm -rf /tmp/qingliu-new && mkdir -p /tmp/qingliu-new
tar -xzf /tmp/qingliu-release.tar.gz -C /tmp/qingliu-new
cp /opt/qingliu/qingliu /opt/qingliu/qingliu.bak-$TS
systemctl stop qingliu
install -m 755 /tmp/qingliu-new/bin/qingliu-amd64 /opt/qingliu/qingliu
rsync -a --delete /tmp/qingliu-new/frontend/dist/ /opt/qingliu/frontend/dist/
rsync -a /tmp/qingliu-new/fonts/ /opt/qingliu/fonts/
systemctl start qingliu && sleep 2 && curl -fsS http://127.0.0.1:8787/health
REMOTE
```

> 坑：`ExecStart` 是 `/opt/qingliu/qingliu`，**不是** `.../bin/qingliu-amd64`；只更新后者不生效。静态 SVG 也由 Go 提供，新增根目录资源要检查 `main.go` 的 `.svg` 分支。

**回滚**：`systemctl stop` → 恢复 `qingliu.bak-<TS>` 与对应 `dist` 快照 → 按备份点恢复数据库（结构不兼容时必须先恢复库，不能只回退二进制）→ 启动并 `/health`。`VAULT_KEY` 不变才能解密旧文件。

## 5. Nginx 与数据库

- 80 仅 ACME + 301；443 反代 `127.0.0.1:8787`
- `/api/login` 单独 `limit_req`；`client_max_body_size 64m`；读写超时 130s
- 安全头：HSTS、X-Content-Type-Options、Referrer-Policy、X-Frame-Options
- 业务不缓存；`/assets/` 带哈希长缓存
- 站点配置在服务器 `/etc/nginx/sites-available/qingliu.bujiaban.top.conf`，示例见 `deploy/nginx.conf.example`

```sql
CREATE DATABASE qingliu CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'qingliu'@'localhost' IDENTIFIED BY '...';
GRANT SELECT,INSERT,UPDATE,DELETE,CREATE,INDEX,REFERENCES ON qingliu.* TO 'qingliu'@'localhost';
```

DSN 与口令在 `/etc/qingliu/qingliu.env`（0600）。不要用 root 跑应用。

## 6. 日常检查

```bash
systemctl status qingliu && systemctl status nginx
journalctl -u qingliu -n 100 --no-pager
curl -fsS http://127.0.0.1:8787/health     # {"status":"ok"}
mysqladmin ping; df -h; free -h
du -sh /var/lib/qingliu /var/backups/qingliu
```

进程 active 不算健康，必须 `/health` 通过。清流上限 `MemoryMax=1G`、`CPUQuota=200%`、`GOMEMLIMIT=512MiB`；同机还有工作台和 MySQL，需一起看。不要记录密码、`VAULT_KEY`、工作台 token 或客户敏感字段。

## 7. 备份与恢复

`/usr/local/sbin/qingliu-backup.sh` 备份 MySQL `qingliu` + `/var/lib/qingliu` + `VAULT_KEY`，每日 03:30，保留 30 天，脚本会短暂停服。每月至少做一次恢复到临时库/目录的演练。

恢复：停服 → 重建库并导入 `.sql.gz` → 解包数据到 `/var/lib` → `chown -R qingliu:qingliu && chmod 700` → 用**同一恢复点**的 `VAULT_KEY` → 启动并 `/health`。

证书：`certbot certificates`、`certbot renew --dry-run`、`systemctl reload nginx`；确认自动续期钩子仍在。

## 8. 常见故障

| 现象 | 排查 |
| --- | --- |
| `/health` 503 | MySQL 可达性、DSN/口令、连接数 |
| 带登录态请求全报「处理失败」 | 漏迁移（多为 005/006/007）→ `journalctl` 找 1054 |
| 登录 401 | 工作台 service 账号/密钥、账号停用、本地兜底是否开启 |
| `AUTH_CAPTCHA_REQUIRED` | 前端没带图形验证码，**不是**密码错 |
| 套餐 503 | `WORKBENCH_BASE_URL` 可达性、SKU 是否存在 |
| 二维码不显示 | 订单是否 pending、`code_url` 是否为空、是否过期 |
| 上传 413 | Nginx `client_max_body_size` / 批次限制 |
| 报告 500 | 字体、`DATA_DIR` 权限、`VAULT_KEY`、任务日志 |
| 重启后任务不动 | `ql_jobs` 状态、执行器日志、MySQL 命名锁 |
| 静态资源 404 | 是否在 `dist`、Go 静态分支是否允许该扩展名 |

## 9. 发布后验收

`/health` ok；HTTPS 登录成功且 Cookie 带 Secure/HttpOnly/SameSite=Lax；首页/底稿/充值/移动端无 console error；上传合成 CSV 能解析、任务能排队完成；充值页能加载套餐、下单、显示二维码/倒计时；旧报告仍可下载且 `VAULT_KEY` 未变；`/api/spaces` 未登录返回 401（不是 500）；空间切换后各页换视角且刷新不回退。

## 10. 安全事件与待补

安全事件：停用账号/撤销会话 → 保留日志 → 更换泄露凭据（`VAULT_KEY` 不能直接轮换，需先设计重加密）→ 通知负责人。

待补：异地备份/对象存储 + 备份加密（本机备份不防主机损坏）；监控告警（存活、磁盘、备份失败）与日志轮转；独立服务器/磁盘加密（如合规要求）。

# 12 · 查询与缓存

## 1. 目标

- 列表按服务端分页，不一次拉全量
- 相同查询在短时间内复用结果，切页/返回不重复请求
- 用户可主动刷新并强制绕过缓存
- 写操作后只失效相关缓存，避免看到旧数据
- 敏感数据不落浏览器持久缓存

## 2. 分层

```text
pages              触发查询、展示 loading/error、触发刷新
app/queries        查询键、TTL、缓存失效策略
feature/api        业务接口路径与参数
shared/api/cache   内存缓存原语（Map + TTL）
shared/api/client  网络、CSRF、401、ApiError
```

`app/queries/index.js` 是唯一允许同时依赖多个 feature 的查询编排层；
`shared/api/cache.js` 不引用任何业务模块。

## 3. 缓存实现

- 存储：浏览器内存 `Map`，页面刷新即清空
- 不使用 `localStorage`、`sessionStorage`、Service Worker
- 缓存键使用“资源 + 规范化参数”，例如 `clients:<q>:<page>`、`admin:audit:<search>`
- 过期后下一次读取自动删除并重新请求
- 手动刷新传 `force: true`，绕过已有缓存并覆盖
- 退出登录、401 时清空全部缓存，避免账号间串数据

## 4. 当前 TTL

| 数据 | 键 | TTL | 刷新方式 |
| --- | --- | --- | --- |
| 客户列表 | `clients:<q>:<page>` | 10s | 搜索、翻页、手动刷新、新建客户后失效 |
| 管理员概览（成员） | `admin:overview` | 15s | 手动刷新、成员增删/启停后失效 |
| 操作记录 | `admin:audit:<params>` | 15s | 筛选、翻页、手动刷新、成员变更后失效 |
| 个人信息 | `profile:me` | 60s | 手动刷新、退出登录 |
| 积分余额 | `billing:balance` | 10s | 手动刷新、下单/支付状态变化后失效 |

TTL 是“短期去重”，不是数据一致性保证。涉及资金、权限、报告签发的判断仍以服务端返回为准。

## 5. 主动失效

| 动作 | 失效范围 |
| --- | --- |
| 新建客户 | `clients:*` |
| 新增成员 / 启停成员 | `admin:*` |
| 创建订单 / 支付完成 | `billing:balance` |
| 修改密码 / 退出 / 401 | 全部缓存 |

写接口成功后先失效再重新查询，不允许先读缓存再等待失效。

## 6. 操作记录接口

### `GET /api/admin/audit`

仅管理员可访问。

查询参数：

| 参数 | 说明 |
| --- | --- |
| `page` | 从 1 开始，默认 1 |
| `page_size` | 默认 20，最大 100 |
| `action` | 动作代码，只接受白名单 |
| `user_id` | 按成员筛选 |
| `q` | 搜索成员显示名、动作代码或详情，最长 120 |
| `from` / `to` | ISO 时间范围，`from` 含、`to` 不含 |

响应：

```json
{
  "events": [
    {
      "seq": 128,
      "user_id": "...",
      "customer_id": "...",
      "action": "login",
      "action_label": "登录",
      "category": "account",
      "detail": "",
      "created": "2026-01-01T08:00:00Z",
      "display": "管理员"
    }
  ],
  "count": 45,
  "page": 1,
  "page_size": 20,
  "actions": [{ "value": "login", "label": "登录", "category": "account" }]
}
```

说明：

- `count` 是当前筛选条件下的总数，用于分页
- `actions` 是服务端维护的动作白名单，前端不再硬编码中文动作名
- 未知 `action` 会被忽略，不拼接任意 SQL
- 默认按 `seq DESC` 排序，等价于时间倒序且稳定

### `GET /api/admin`

只返回团队成员，不再附带 100 条操作记录。操作记录统一走 `/api/admin/audit`。

## 7. 数据库索引

`ql_events` 需要：

```sql
INDEX(user_id, seq)
INDEX(action, seq)
INDEX(created, seq)
```

新库由 `schema.sql` 直接创建；已有生产库执行
`server/migrations/001-audit-indexes.sql`。执行前备份数据库，执行后用
`SHOW INDEX FROM ql_events` 确认。

## 8. 后续可选优化

- 操作记录数据量继续增长时，按 `created` 做归档表或冷热分层
- 需要跨实例一致性时，再评估服务端短 TTL 缓存；目前单进程 + 浏览器内存缓存足够
- 若客户列表数据量明显增大，可在 `ql_customers(name)` 或授权关联上补索引，
  并保持现有分页 API 不变

## 9. 验证

```bash
cd server
GOTOOLCHAIN=auto GOOS=linux GOARCH=amd64 go build -o /tmp/qingliu .
GOTOOLCHAIN=auto GOOS=linux GOARCH=amd64 go vet ./...

cd ../frontend
npm run check
npm run smoke
```

真实环境回归：

1. 打开 `/admin`，确认操作记录每页 20 条、总数、翻页正确
2. 切换操作类型/搜索后请求参数变化，页码回到 1
3. 离开再返回 `/admin`，15 秒内不重复请求
4. 点击“刷新”，应绕过缓存重新请求
5. 新增/启停成员后，成员和操作记录均刷新
6. 个人信息页刷新按钮生效；未点击刷新时返回页面复用缓存

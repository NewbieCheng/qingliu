# 架构核查与迁移

核查日期：2026-11-04。服务器前提：8核CPU、4GB内存，共享团队已有MySQL、反向代理及API中转。目标是减少常驻服务与维护分叉，不能仅凭CPU核数承诺容量。

| 项目 | 原项目 | 新交付版 |
|---|---|---|
| 后端 | Python Flask + Waitress；另保留 Streamlit | Go 标准库 HTTP，单个进程 |
| 页面 | Jinja 模板 + 原生 JS | React，Vite构建后由Go提供静态文件 |
| 数据库 | SQLite | 现有 MySQL 的专用库、专用用户 |
| PostgreSQL | 没有 | 没有 |
| Redis/消息中间件 | 没有 | 没有 |
| 后台任务 | SQLite任务表 + Python独立worker | MySQL任务表 + Go进程内单执行器 |
| PDF | PyMuPDF/pdfplumber | Poppler/MuPDF坐标文本提取，Go解析与规则 |
| 扫描征信 | macOS Apple Vision | Linux Tesseract候选 + 人工核对 |
| 报告 | Python生成PDF、Excel、HTML | Go原生生成，认证加密后落盘 |
| AI/中转 | 没有业务调用 | 不新增AI调用；未使用中转地址/Key |
| 浏览器缓存 | 所有请求no-store | 业务no-store；哈希静态资源长期缓存 |

团队程序员关于统一维护栈、避免重复数据库和提前引入Redis/消息队列的建议适用于本项目。附图提到的“不同语言必然冲突、服务器会很快卡顿”不是本机测试结果；实际资源取决于进程、并发与任务大小。当前没有证据说明原项目用了PostgreSQL或Redis。

选择单执行器是因为PDF、中文PDF输出与OCR比普通HTTP请求更耗内存。任务排队写MySQL，关闭浏览器不会取消；MySQL命名锁只允许一个执行器恢复中断任务。实例失去执行器数据库连接时退出，由部署层重启。客户修改与后台处理使用同一客户锁，处理期间阻止修改；不引入分布式调度、微服务、服务注册或消息系统。

仅一个应用进程；HTTP最多4个并发处理槽，数据库连接池最多8，容器2CPU/1GB上限，Go软内存目标512MiB。/tmp最多768MB（计入容器内存），逐页OCR，避免全部扫描页同时渲染。上述是初始限制，并非压力测试得出的容量保证；上线后在团队服务实际共存的环境观察峰值内存和排队时间。

缓存：React有版本哈希的assets目录使用1年immutable，入口HTML、登录、客户数据、PDF原页与报告下载no-store；无localStorage、IndexedDB、Service Worker或离线客户缓存，权限变更后仍由后端逐次检查。

安全：bcrypt密码，服务端随机会话与CSRF，HTTPS时Secure/HttpOnly/SameSite Cookie，5次失败后15分钟限制（按直接连接IP+账号；代理后的共享IP限制更保守），按客户授权、审计、AES-256-GCM文件认证加密、报告SHA256完整性校验。MySQL中的业务字段未额外字段级加密，需使用现有加密磁盘和数据库备份策略。初始管理员只由服务器CLI创建，网页不开放首次注册。

原项目源码及旧档案保留在本地原目录，新版独立放在 `delivery/qingliu/`；避免覆盖已有客户和历史复核。部署包为空库启动，不含自动历史数据迁移工具。

技术参考：React官方独立构建说明 https://react.dev/learn/build-a-react-app-from-scratch ，MySQL命名锁 https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html ，Go发行版 https://go.dev/dl/ 。版本以随包锁文件和二进制为准。

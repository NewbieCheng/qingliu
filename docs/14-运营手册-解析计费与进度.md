# 运营手册：文档解析、计费与进度

> 面向运营与客服。按「我要做什么」组织，每一步都给出点哪里、看什么、异常怎么办。
> 技术细节见 `docs/计划-v2-解析计费与登录安全.md`。

---

## 1. 先理解一件事：解析有三条路，只有一条花钱

清流收到 PDF 后会自己判断走哪条路，**能免费就不花钱**：

| 顺序 | 路径 | 什么时候走 | 计费口径 |
| --- | --- | --- | --- |
| 1 | 文字层提取 | PDF 里本来就有可复制的文字（多数银行/微信/支付宝导出的证明） | 按**份** |
| 2 | 本机 OCR | 文字层取不到（扫描件、拍照件） | 按**页** |
| 3 | 视觉模型 | 本机 OCR 也认不出来，且用户主动点「文档视觉识别」 | 按**页**，最贵 |

关键点：
- **第 3 条不会自动发生**。系统只会提示「建议使用文档视觉识别」，必须用户在界面上确认，避免不知情扣费。
- 实际效果：129 页的微信账单走的是第 1 条，扣 1 积分，而不是 129 次模型调用。

## 2. 改价格（运营最常用）

### 2.1 在哪里改

1. 登录工作台后台 `https://worker.no996ai.cn/console/`（测试环境是 `worker.bujiaban.top`）
2. 左侧菜单 **运营 → 财务**
3. 页面下方找到 **「文档解析计价」** 卡片

### 2.2 三个数字分别是什么

| 字段 | 含义 | 举例 |
| --- | --- | --- |
| 文字层提取（积分/份） | 一份文档走文字层要多少分 | 填 `1`：129 页微信账单收 1 分 |
| 本机 OCR（积分/页） | 每一页本机识别要多少分 | 填 `1`：10 页扫描件收 10 分 |
| 视觉模型（积分/页） | 每一页模型识别要多少分 | 填 `5`：10 页扫描件收 50 分 |

**填 0 = 该档免费。** 三个都填 0 就等于解析完全不收费。

### 2.3 改完多久生效

点「保存」后，清流最多 **60 秒** 内自动生效，**不需要重启任何服务**，也不影响正在解析的任务（正在跑的任务按启动时的价格结算）。

### 2.4 调价建议

- 视觉模型一定要明显高于本机 OCR，否则用户会无脑点 OCR，成本压不住。
- 如果想让用户多用文字层，把「文字层提取」调到 1–2 分，OCR 调到 5–10 分/页。
- 活动期想免费，只把「文字层提取」改成 0 即可，两条 OCR 保持不变（成本仍可控）。

## 3. 看进度和排队

### 3.1 用户看到什么

上传后，任务卡片会实时显示：

```
[██████████░░░░░░]  62%
正在识别第 78 / 129 页
```

- **百分比**：按真实页码换算，从 5% 开始，解析完成 95%，全部结束 100%。
- **阶段文字**：`排队中` → `正在识别第 x / y 页` → `已扣除 N 积分` → `完成`
- **失败时**：进度保留在失败那一刻，并给出具体原因（不是一句「解析失败」）。

### 3.2 作为运营怎么看任务

直接查数据库（只读，不会影响业务）：

```sql
-- 正在排队和运行的任务，按提交顺序
SELECT id, kind, status, stage, progress, message, created
FROM ql_jobs
WHERE status IN ('queued','running')
ORDER BY seq;
```

`progress` 列就是界面上那个百分比。`stage` 是阶段，`message` 是给用户看的中文。

### 3.3 为什么用户要排队

- 服务器是 2 核 / 1 GB，解析是 CPU 密集型。
- 当前**单进程串行**处理：同一时刻只解析一份，其他排队。
- 这是刻意的：并发会让内存爆掉，导致所有任务一起失败。
- 用户在同一次上传里选多份文件，会按选择顺序自动排队，不需要重复点击。

### 3.4 任务卡住怎么办

```bash
ssh root@115.191.68.41
journalctl -u qingliu -n 50 --no-pager     # 看最近日志
```

- 日志出现 `parse charge skipped`：该账号没绑定工作台身份，解析成功但不扣费。让用户用工作台账号重新登录一次即可绑定。
- 日志出现 `parse pricing load failed`：后台计价读不到，检查 `no996-backend` 是否正常。
- 任务长期 `running` 不动：重启 `systemctl restart qingliu`，重启会把中断的任务重置为排队并自动重跑。

## 4. 扣费怎么发生（给客服的解释口径）

### 4.1 规则

1. **成功才扣，失败不扣。** 解析失败、或者文件有问题没解析出来，一分不收。
2. **同一份文件不会重复扣。** 系统按文件内容指纹（sha256）去重，24 小时内重复上传同一份文件不再收费。
3. **余额不足会提前拦下。** 用户点上传时就会被提示「积分不足，请联系管理员充值」。

### 4.2 怎么查某一次扣费

```sql
-- 按批次号查（批次号形如 qingliu-parse-<任务id>）
SELECT ledger_id, owner_type, owner_id, batch_trace_id, reason,
       points_delta, points_balance_after, created_at
FROM t_point_ledger
WHERE reason LIKE 'qingliu_parse%'
ORDER BY ledger_id DESC
LIMIT 20;
```

- `reason` 会写明是哪一档：`qingliu_parse_text` / `qingliu_parse_ocr` / `qingliu_parse_vision`
- `points_delta` 是负数，表示扣了多少
- `points_balance_after` 是扣完后的余额，可直接对账

### 4.3 用户说「我没用怎么被扣了」

按顺序核对：
1. 用上面的 SQL 查到那次扣费的 `batch_trace_id`
2. 用批次号里的任务 id 查 `ql_jobs`，看 `status` 是否 `done`
3. 如果任务确实完成了，说明确实解析成功，扣费正常
4. 如果任务状态是 `failed` 却有扣费 → 这是故障，登记并报技术处理

## 5. 接口调用说明（给对接方）

清流与工作台之间的解析计费走两个接口，都用**服务凭证**（不走用户令牌）：

### 5.1 读价格

```http
GET /api/v1/service/billing/parse-pricing
X-Service-Client: qingliu
X-Service-Secret: <服务密钥>
```

返回：

```json
{
  "data": {
    "text_points_per_document": 1,
    "ocr_points_per_page": 1,
    "vision_points_per_page": 5
  }
}
```

### 5.2 扣积分

```http
POST /api/v1/service/billing/charge
X-Service-Client: qingliu
X-Service-Secret: <服务密钥>
Content-Type: application/json

{
  "workbench_user_id": 21,
  "points": 1,
  "batch_trace_id": "qingliu-parse-<任务id>",
  "reason": "qingliu_parse_text"
}
```

- `batch_trace_id` 是**幂等键**：同一个值重复提交只会扣一次。重试时务必传同一个值。
- 返回里带 `points_delta` 与扣后余额，便于对账。

### 5.3 调用顺序（清流内部逻辑）

```
用户上传 → 检查余额（<0 直接拒绝）
        → 入队排队
        → worker 取出任务
        → 判断走哪条路解析（文字层 / 本机 OCR）
        → 解析成功
        → 读价格 → 按实际路径算分 → 调 charge 扣费
        → 任务标记完成
```

解析失败时直接跳到「标记失败」，**不会调用 charge**。

## 6. 常见问题速查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 用户说「积分不足」 | 余额 ≤ 0 | 后台「运营 → 流水查询」充值 |
| 解析成功但余额没变 | 账号未绑定工作台身份 | 让用户用工作台账号重新登录 |
| 解析很慢 | 单进程串行排队 | 正常现象；看 `ql_jobs` 里排队数 |
| 提示「建议使用文档视觉识别」 | 该页没有文字层，本机 OCR 也认不出 | 让用户点 OCR 按钮，会按页收费 |
| 同一份文件第二次上传被拒 | 内容去重 | 正常行为，换文件或删掉旧记录 |
| 调价后价格没变 | 缓存 60 秒 | 等一分钟 |

## 7. 数据隔离说明（重要）

- **企业登录**看到的是整个团队的资料，团队内成员共享。
- **个人登录**只能看到自己创建的客户，与其他个人、任何团队都**完全隔离**。
- 管理员也受同样约束，不能跨团队查看。
- 如需跨团队核对，必须由对方团队账号导出，或走合规审批流程，不要直接改数据库。

## 8. 实测记录（2026-11-09，生产环境）

用真实账单在生产服务器上跑通全链路，结果如下。

### 8.1 三份真实账单

| 文件 | 页数 | 解析路径 | OCR 页数 | 交易条数 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 微信支付交易明细(20251001-20260930) | **129** | 文字层 | **0** | 15294 | success |
| 微信支付交易明细(20260927-20261027) | 9 | 文字层 | 0 | 978 | success |
| 支付宝交易明细(20251028-20261027) | 6 | 文字层 | 0 | 948 | success |

**要点**：129 页那份有 25.6 万字，远超旧代码的 12 万字截断阈值 —— 这就是当初「文件解析失败」的真正原因。现在全量解析，且**一页 OCR 都没用**，印证了「有字就取字、不浪费积分」的设计。

### 8.2 多用户并发排队

两个客户同时提交（A 传 2 份、B 传 1 份，共 3 个任务）：

- 三个任务按提交顺序入队：`seq 29 / 30 / 31`
- 采样期间 `running` 计数始终 ≤ 1，**严格串行**
- 三份全部 `success`，均走文字层，0 页 OCR
- 扣费 3 次各 1 分，余额 1000 → 997
- 日志逐条可查：`parse charge ok: job=... method=text pages=129 points=1`

### 8.3 余额拦截

余额为 0 时上传直接被拒：`积分不足，无法解析；请联系管理员充值后再上传`（HTTP 402），不会先收文件再失败。

### 8.4 数据清理

测试产生的客户、文档、任务、账本记录与临时库已全部删除，积分余额还原到测试前数值，`QINGLIU_ALLOW_LOCAL_LOGIN` 开关已移除。

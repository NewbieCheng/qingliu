# 交付记录 · 中行末页页脚粘连修复

> 日期：2026-11-23  
> 范围：`server/parser.go`、`server/domain.go`、`server/footer_filter_test.go`  
> 生产案例：`KA0200039b4b3384ddb0001（1）.pdf`（28 页 / 406 笔，`partial` + 第 28 页 expense 控制总额未通过）

## 1. 当初怎么设计的（不要拆掉）

流水解析有三道故意留下的闸：

| 闸 | 作用 | 为什么要 |
| --- | --- | --- |
| **页脚过滤** `isPageFooterLine` | 丢掉「打印时间 / 本页收支…」等非交易行 | 招行页脚曾被当成交易 → 整份拖成 partial |
| **页合计核对** | 用页头「借方发生数 / 贷方发生数」对照本页抽出金额 | 银行自己印的控制数当质检尺；对不上说明漏抽/错抽 |
| **导诊** `explainIssue` | 把 issue 译成人话 + 可点按钮 | 业务员不用读技术字段 |

设计口径：**宁可疑（partial/suspect），不可装成功**。页合计核对不是多余告警，是安全网；本次修复**保留核对，只修抽数**。

## 2. 这次为什么触发

生产只读取证（`ql_documents.id=b1bb7eeedc29d5e5774da62223fec693`）：

1. 中国银行流水末页常只有 **1 笔**交易。
2. 旧逻辑在「本页仅 1 个日期锚点」时，末行底边落到近页底（`Height-20`），把「温馨提示 / ----END----」吸进单元格。
3. 金额格变成：`-17.091.记账日期/时间为系统…` → `quality=invalid`。
4. 硬规则：`第28页expense控制总额核对未通过` + `部分交易字段无效` → `status=partial` → 导诊条出现。

页合计核对**报得对**；病灶在抽数，不在核对。

## 3. 怎么修（两边都通）

1. **末行底边**：任意流水末行扫描页脚锚点（`温馨提示` / `----END----` / `说明:` / `第N页`），裁掉页脚再抽格。
2. **页脚行识别**：中行单特征（温馨提示 / END / 第N页/共M页）即可判为页脚并跳过。
3. **金额净化**：解析路径先 `sanitizeMoneyToken` 截取开头合法金额（最多两位小数），再交给 `cents`（`cents` 本身不放宽格式，避免误收科学计数法等）。
4. **不关页合计**：真漏行/金额错仍 `partial` + 导诊。

## 4. 业务侧操作（发版前后）

- 已入库的脏件：打开「字段核对」改第 28 页脏行，或「核对后重新解析」（新二进制生效后重跑）。
- 加密件仍须先解密再传（同客户更早两次 `method=encrypted` 失败与本次无关）。

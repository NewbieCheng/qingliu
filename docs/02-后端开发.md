# 02 · 后端开发

## 1. 形态

**一个 Go 进程**，标准库 `net/http`，不依赖 Web 框架、ORM、Redis、消息队列或第二个常驻进程。它同时提供 `/api/*` JSON、`/health`、同源 React 静态产物，并在进程内跑单执行器处理解析/报告/AI 分析。入口 `server/main.go`，模块名 `qingliu`，Go 1.26。

## 2. 启动配置

生产通过 `/etc/qingliu/qingliu.env` 注入（不提交真实值）。代码实际读取的变量：

| 变量 | 说明 |
| --- | --- |
| `MYSQL_DSN` | MySQL 8 DSN，专用库/用户 |
| `PUBLIC_ORIGIN` | 唯一外部源，不带末尾斜杠；决定 Cookie 是否 `Secure` |
| `VAULT_KEY` | 64 位 hex，AES-256-GCM 文件加密；不可随意更换 |
| `DATA_DIR` | 加密原件与报告目录 |
| `STATIC_DIR` | `frontend/dist`（默认同值） |
| `PDF_FONT` | 中文 PDF 字体 |
| `LISTEN_ADDR` | 默认 `127.0.0.1:8787` |
| `GOMEMLIMIT` / `GOMAXPROCS` | 资源约束（运行时读取） |
| `WORKBENCH_BASE_URL` | 工作台后台地址 |
| `WORKBENCH_SERVICE_CLIENT` / `WORKBENCH_SERVICE_SECRET` | service login 凭证 |
| `QINGLIU_ALLOW_LOCAL_LOGIN` | `1` 时允许本地密码兜底登录 |
| `AUDIT_RETENTION_DAYS` / `AUDIT_LOGIN_RETENTION_DAYS` | 操作记录留存，默认 90 / 30 |
| `COLD_DATA_RETENTION_DAYS` | `ql_jobs` / `ql_upload_batches` 中间态保留，默认 30 |
| `AI_ANALYSIS_RETENTION_DAYS` | `ql_ai_analyses` 终态保留，默认 60 |
| `TEMP_CACHE_RETENTION_DAYS` | `DATA_DIR/pending` 与 OS 临时切页目录保留，默认 7 |
| `QL_STRUCTURE_MODEL` | 上传结构化补救所用聊天模型，默认 `deepseek-chat` |

`init-admin` 子命令额外读 `ADMIN_USERNAME` / `ADMIN_PASSWORD`；库里已有账号时初始化自动关闭。

启动执行 `schema.sql` 的 `CREATE TABLE IF NOT EXISTS`，不清空旧表，也**不会给已有表补列**——结构变更必须另做版本化迁移并手动执行。

## 4. 会话、空间与授权

- 登录生成随机会话 token 存 `ql_sessions`；Cookie `HttpOnly; Secure; SameSite=Lax`（HTTPS 时）
- 会话行带 `space_kind` / `space_id`（**本会话所在空间**），授权判定读它而不读用户上的列
- 每会话一个 CSRF token，前端从 `/api/me` 取，写请求带 `X-CSRF-Token`；业务响应 `Cache-Control: no-store`
- 登录失败按 IP+账号计数，5 次锁 15 分钟；Nginx 另有 `limit_req`
- 本地密码 bcrypt（仅 `QINGLIU_ALLOW_LOCAL_LOGIN=1` 可用）；工作台侧只认 argon2id
- 权限判定走 `q.can(code)`（读 `ql_workbench_accounts.permissions` 快照），`ql_users.role` 只是兜底
- 资料/报告用 AES-256-GCM 加密落盘，报告带 SHA256

`scopeWhere(access customerAccess, alias)` 是授权判定与列表查询的**唯一口径**：

| 情况 | 可见范围 |
| --- | --- |
| 团队 + 管理员 | 本企业全部客户（`workspace_tenant_id = 空间 id`） |
| 团队 + 非管理员 | 本企业**且** `ql_grants.workbench_user_id` 命中自己；无工作台 id 则 `1=0` |
| 个人/平台 + 已绑定工作台 | 自己创建的，或被授权给 `workbench_user_id` 的 |
| 个人/平台 + 未绑定 | 自己创建的，或被授权给本地影子 `user_id` 的 |

```go
// 团队 + 非管理员（节选）
return alias + ".workspace_tenant_id=? AND EXISTS (" +
    "SELECT 1 FROM ql_grants g WHERE g.customer_id=" + alias + ".id AND g.workbench_user_id=?)",
    []any{access.Space.ID, access.WBUserID}
```

平台空间刻意走「只看自己」：清流没有平台视图，平台令牌绝不放宽到某团队全部资料。管理员也不能跨企业——`role=="admin"` 无条件放行的旧漏洞已修掉。`Store.allowed` 与列表共用这份实现，否则会出现「列表看不到、直接输 ID 却能打开」的越权。

## 5. 工作台桥接

`loadWBConfig()` 读取 `WORKBENCH_BASE_URL`、`WORKBENCH_SERVICE_CLIENT`、`WORKBENCH_SERVICE_SECRET`。

- `POST /api/v1/service/auth/login`，body `{email, password, service_code:"qingliu", captcha_id, captcha_code}`，带 `X-Service-Client` / `X-Service-Secret`
  - **验证码是硬要求**：工作台在密码校验前就查，缺了返回 `AUTH_CAPTCHA_REQUIRED`（401）——不是登录失败
  - 账号必须在 `t_user_service` 里有 `qingliu` 且 `status=1`，否则 `AUTH_SERVICE_SCOPE_MISMATCH`（403）
- 拿到 token 后加密存 `ql_workbench_accounts`，同时存权限码快照 `permissions`
- 后续计费请求用 `Authorization: Bearer <access_token>`，过期用 refresh token 刷新
- 浏览器永远看不到 service secret 或工作台 token

### 5.1 工作台令牌与「请重新登录工作台账号」（Agent 必读）

| 层 | TTL | 存哪 |
| --- | --- | --- |
| 清流 Cookie `ql_session` | **8 小时** | `ql_sessions` |
| 工作台 access token | **默认 15 分钟**（后端 `defaultAccessTokenTTL`） | 加密进 `ql_workbench_accounts.access_token` |
| 工作台 refresh token | 约 30 天，**一次性轮换** | 加密进 `ql_workbench_accounts.refresh_token` |

用户症状：「清流还登着，充值/余额突然要重新登录工作台；大约一刻钟一次；本地也没人挤号」。  
根因**不是** Cookie 过期，也**不是**账号被别处登录，而是：

1. access 快过期时，`wbAccessToken` / `wbRequest(401)` 会调 `wbRefresh` → 工作台 `POST /api/v1/auth/refresh`。
2. 工作台 refresh **轮换**：旧 refresh 立刻作废；再拿旧的去刷 = `ErrRefreshTokenReused` → **吊销整个 family**（新 access/refresh 一起废）。
3. 充值页顶栏 `queryBalance` 与正文 `getSkus`/`getBalance` 等会**并发**打 `/api/billing/*`；到期窗口内若两次 `wbRefresh` 并行，就会自踢。
4. 清流 Cookie 仍有效，所以只看到业务接口 503「请重新登录工作台账号」（请求 id 形如 `r-xxxxxx`），其它工作台代理（空间名、成员、AI 上传）也会一起挂。

**硬约束（改 `workbench.go` 时）：**

- 同一本地 `user_id` 的 refresh 必须单飞（`App.refreshGates`）；禁止无锁并发 `wbRefresh`。
- **单飞的收尾必须无条件执行**：`gate` 登记后，成功、失败、**panic** 三条路径都要 `delete(a.refreshGates, userID)` + `close(gate.done)`（用 `defer` 里 `recover()` 统一收尾）。少关一次，该用户后续每个请求永久卡在 `<-gate.done`。
- **等待方必须带超时**：`select { case <-gate.done: … case <-time.After(wbRefreshWaitTimeout): 报错退出 }`。领飞者卡死时不能陪葬。
- 记住并发放大效应：准入是**分档**的（`server/pool.go`：read 64 / write 32 / proxy 32 / bulk 2 / render 4，`/health` 与静态资源不入池）。任何一档被长期占满都会让该档接口持续 503，进程却仍 `active`、看起来像「没崩但打不开」；所以阻塞点必须在代码里兜死，而不是靠池子大小兜。
- **准入按代价分档，禁止退回「全站一个池」**：`route()` 用 `poolFor()`（`server/pool.go`）把请求分到 read 64 / write 32 / proxy 32 / bulk 2 / render 4；`/health`、HTML、`/assets/*`、`*.svg` **不入池**；满池先排队（200ms–2s）再 503 + `Retry-After`。历史教训：初始交付把 4 个槽管住全站，一次充值页并发就能让首页 503（[05 §11](05-部署与运维.md)、[§12](05-部署与运维.md)）。
- **临时的重活要单独占档，不要挤别人的档**：新增同步重活（渲染、转换、大文件）时，先判断它属于哪个档；确实更重就加一档并给独立环境变量，别把 `read` 或 `proxy` 调小。
- 不要把工作台宕机/网络错误一律折叠成「请重新登录」；refresh 失败文案要区分（已有回归：`workbench_token_test.go`）。
- 不要把 access TTL 误当成清流会话 TTL；也不要靠前端轮询去「保活」refresh。
- 复现单测：`server/workbench_refresh_test.go`（并发复用吊销 family + singleflight 合并）。事故复盘见 [05-部署与运维 §11](05-部署与运维.md#11-故障档案2026-11-12-全站-503-假死wbrefresh-gate-泄漏)。

## 6. 执行器 · 排队 · 批量

三种「排队」不要混：

| 机制 | 代码 | 作用 |
| --- | --- | --- |
| HTTP 准入池 | `pool.go`（read/write/proxy/bulk/render） | 请求进进程前限流；满池短等再 503 |
| 后台任务队列 | `ql_jobs` + `workerLoop` 单执行器 + `GET_LOCK('qingliu:worker')` | 真正的解析/报告/智析排队；全局一次只跑一条 job |
| 解析通道 DocKind | `parse_pipeline` 内同步分发 | **不是**排队，是单任务内选处理器 |

`ql_jobs`：`queued` → `running` → `done`/`partial`/`failed`；关浏览器不取消。同客户再加 `GET_LOCK('case:'+cid)`（客户内也串行）。策略表 `jobPolicy(kind)`（`job_policy.go`）：

| kind | RunTimeout | Stale | LocksBusy | 说明 |
| --- | --- | --- | --- | --- |
| `upload` | 15min | 45min | **是** | 入队解析；锁 `busy()` |
| `report` | 8min | 30min | **是** | 出件；锁 `busy()` |
| `ai_analysis` | 25min | 90min | **否** | 核对步智析旁路；只进 `jobs_live`，不挡勾选/保存 |

`busy(cid)` 只认未超时的 `upload`/`report`；超时仍 queued/running 的由 `sweepStaleJobs` 按 kind stale 扫掉，防止一条僵尸任务永久 409。前端任务坞用 `jobs_live` + `queue_position` 显示「前面还有 N 个」。

### 6.0 批量上传与批量智析

**上传批量（一次最多 10 份）**

1. `POST /upload`（或本机拆行后 `/upload-parsed`）整批校验 → 每份写一条 `ql_jobs(kind=upload,status=queued)`，同批带 `upload_batch`。
2. `ql_upload_batches` 存批次回放载荷：同 `batch` 重试幂等，不重复建任务。
3. worker 按 `seq` 取队首依次跑；混传允许 PDF/CSV/XLSX/DOCX/图片同批。

**AI 智析批量（一次最多 10 份，服务端串行入队）**

1. `POST /api/clients/{cid}/ai-analysis`：`document_id` 或 `document_ids`（≤10）；循环 `startAIAnalysis`，一次请求内**串行建多条** `ql_ai_analyses` + 对应 `ql_jobs(kind=ai_analysis)`。
2. 返回 `{analysis, analyses, count}`；真正执行仍走单执行器队列（与 upload 共用 worker，但 **不**置 `busy`）。
3. `task=page_ocr` 走视觉转写；`task=person_merge` + `analysis_ids`（2–5）只吃摘要合并，不重传原件。
4. 前端矩阵「批量开始」调同一 API（`features/ai-analysis/api.js`）；进度角标看 queued/running/done。

详细时序图仍可参考历史计划稿 [计划-解析链路… §12](计划-解析链路修复与AI参与+本地自动化测试准备.md)；**现行权威以本节 + [01 §6.2](01-前端开发.md) 为准**（行号可能漂移）。

### 6.1 上传解析瀑布（现行权威顺序）

上传任务支持 **PDF / CSV / XLSX / DOCX / 图片（PNG / JPG / JPEG / WEBP）混传**；`POST /api/clients/{cid}/upload` 先做全批校验（`http.MaxBytesReader` 64MB、份数 1–10、单文件 ≤30MB、单张图片 ≤20MB、**整批总体积 ≤60MB**、PDF/DOCX/图片魔数校验、SHA-256 去重）后再入队。**前端不再提供「本地 OCR」勾选**，闸门只看解析结果。

**流水质检三闸（勿拆）**：① 页脚过滤（招行「打印* / 本页收支」+ 中行「温馨提示 / END / 第N页/共」）；② 页头借/贷发生数与本页抽出金额核对；③ 失败才导诊。末页仅 1 笔时必须按页脚锚点裁底边，否则页脚会粘进金额格 → 假 partial。案例与修法见 [交付记录-中行末页页脚粘连修复](交付记录-中行末页页脚粘连修复.md)。

```text
1. 浏览器快速拆行（CSV/XLSX/瘦 DOCX → POST /upload-parsed）或服务端 parseFile（CSV/XLSX/DOCX XML/有字 PDF 文字层/图片标记 needs-vision）
   · 混传时若 source=other，CSV/XLSX/DOCX 按表头与正文特征自动推断微信/支付宝/银行来源
2. 若仍无标准交易行且命中 shouldTryWorkbenchOCR（图片或扫描/未对齐流水 PDF；DOCX 跳过 /v1/ocr）
   → POST /v1/ocr（通道由工作台选；清流不写厂商 if/else）
3. 征信图片（credit_report）将 OCR 正文写入 facts 并置 status=success；流水类 parseOCRTranscript 能解析 → 入库，method=workbench-ocr
4. 不能 → 模型结构化补救（/v1/chat/completions，method=workbench-structure；含 DOCX 提取的 extract_text）
5. 仍不行 → status=partial，保留 ocr_text / facts 供人工核对
```

| 要点 | 口径 |
| --- | --- |
| OCR 触发 | 图片（PNG/JPG/WEBP）直接走 `/v1/ocr`；PDF 为 `needs-vision` 或流水类已有文字/`extract_text` 但 0 行；DOCX 仅走 `extract_text` 结构化补救不发 `/v1/ocr`。PDF 征信不因「无交易行」误触发 |
| 结构化补救 | 只整理成标准交易行；**不**写 `ql_ai_analyses`，与核对步「AI 智析」分离 |
| 计费 | `workbench-ocr` / `workbench-structure` 均归入 `parseBillingTier=workbench-billed`（0 分），禁止清流再扣一遍 |
| 回退 | `/v1/ocr` 调用失败时：若本地已有 `extract_text`，仍可尝试结构化补救；智析任务 `page_ocr` 另可回退 aidoc / 本机 tesseract |

实现：`ai_analysis.go`（闸门与 OCR 合入）+ `structure_rescue.go`（补救）+ `worker.go`（上传任务调用）。

### 6.2 超时 / 轮询（现行）

| 层级 | 怎么生效 |
| --- | --- |
| **全局统一** | `jobPolicy(kind)`、cancel/stall 判定、前端 `useJobPoll`；进度用轮询（不做推送） |
| **按 kind 配数** | stale / 执行预算 / 轮询间隔 / 是否锁 busy —— **禁止**全站一个魔法分钟数覆盖 upload 与百页 page_ocr |
| **同类型复用** | 新增长任务只加策略表一行 + 执行器；禁止再复制 setInterval / 再造 cancel 通道 |

工作台 aidoc 侧按 `task` 配 budget、cancel/SSE；运维见工作台 [`operations-runbook.md`](../../不加班智能团后端/docs/development/operations-runbook.md)「任务中心…」。与 `gentask`（口型/视频）**概念对齐、表不合并**。验收背景见 [计划-清流减负与AI赋能总册](计划-清流减负与AI赋能总册.md)。

`sweepStaleJobs` **按 kind 读 stale**，与工作台 analysis budget 对齐，避免清流先失败、工作台仍在跑。

上传瀑布与核对步 AI 智析不要混用同一套文案：前者产出交易行，后者产出摘要/异常/预勾（前端入口只在 `ReviewStep`，见 [01 §6.1](01-前端开发.md)）。

## 8. 不要做

不引入第二个数据库/Redis/队列解决单机任务；不在浏览器存 service secret 或模型 Key；不改 `VAULT_KEY`、不绕过 `Store.seal/unseal` 写文件；不直接改线上表而不回写迁移；不写 `role == "admin"` 这类硬编码判定。

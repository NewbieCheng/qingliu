# 00 · 项目总览

## 1. 产品定位

清流（Qingliu）是面向业务员、复核员和管理员的**客户资料与银行流水初筛工作台**。它解决内部初筛阶段的证据留存和人工核对，不是银行信贷审批系统。

品牌关系：母品牌「今天不加班」→ 产品「青流」，主张「资料有据 · 测算有序」。

## 2. 四步流程

1. **上传资料**：PDF / CSV / XLSX；每批 1–10 份、单份 30MB、整批 64MB、PDF 1–500 页。
2. **确认归属**：确认客户、资料归属和纳入范围；支持人工关联名单。
3. **逐笔核对**：查看解析出的交易、疑点、PDF 原页对照，标记确认/排除/待补。
4. **生成报告**：草稿 → 提交复核 → 复核通过 → 正式内部初筛报告（PDF / Excel / HTML 快照）。

旧资料不会自动纳入新客户；正式报告是快照，后续资料变化不会覆盖已生成报告。

## 3. 角色与权限

角色和权限**由工作台投影而来**（`server/permissions.go`），清流不自己维护：

| 角色 | 能力 |
| --- | --- |
| `admin` | 工作台成员管理代理、客户、全部报告、授权 |
| `sales` | 获授权（及自己创建）的客户、上传、核对、草稿、提交复核 |
| `reviewer` | 被授权的客户、复核、签发正式报告 |
| `readonly` | 只读成员：只看获授权资料与账单，**不能**上传/核对/签发 |

权限码：`qingliu.admin`、`qingliu.case.read`、`qingliu.case.write`、`qingliu.report.sign`、`qingliu.member.manage`、`qingliu.billing.read`、`qingliu.billing.recharge`。服务端每个写接口各判一次 `q.can(code)`，前端按 `/api/me` 下发的快照显示/隐藏入口。

**账号真相只在工作台**：登录、密码、启停、企业成员都由工作台判定；`ql_users` 是登录时自动生成的**影子行**，只给会话/任务/操作记录当外键。清流唯一的业务绑定是 `ql_grants.workbench_user_id`（客户授权给谁）。

空间（个人 / 企业 / 平台）是**会话**属性，可在个人中心切换；资料隔离由 `scopeWhere` 按「会话空间 + 工作台身份授权」判定，详见 [02-后端开发](02-后端开发.md) §4。

## 5. 运行形态

- 一个 Go 二进制同时提供 API + React 静态文件；没有 Node 常驻进程。
- MySQL 独立库 `qingliu`，不与工作台共用表。
- 后台任务在 Go 进程内单执行器运行；任务写 `ql_jobs`，浏览器关闭不取消，重启可恢复。
- 原始资料和报告以 QLGO1（AES-256-GCM）落在 `DATA_DIR`；数据库只存索引/元数据。
- 计费与支付订单不落清流库，统一代理到工作台后台。

## 7. 重要边界

- 不承诺"识别所有银行/征信版式"；新版式必须逐项核对行数、方向、金额、总额、日期口径。
- OCR 只给原文候选，不自动认定征信余额或贷款资格。
- 不做自动贷款审批、授信结论或对外正式报告；报告仅供内部初筛。
- 不在浏览器保存平台模型 Key、支付签名或服务端凭证。
